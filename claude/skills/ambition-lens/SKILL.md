# Ambition Lens

依頼をそのまま実行する前に、**ゴールの先のゴール（Altitude）・その道の第一人者の水準（Depth）・他分野の視点（Range）** で明らかに良くなるかを見極める。良くなるなら、依頼を書き換えた具体案を選択肢にして **1問だけ** 聞き返す。ユーザーは選ぶだけで、野心的な依頼文に格上げされる。**Speed** は元の依頼どおり速くやることを指し、選択肢では「そのまま」に当たる。

記事の各テクニック・例・問いの言い回しは [references/techniques.md](references/techniques.md) にある。書き換え案を作る時に読む。例は型の見本であり、同じ構成をなぞる必要はない。

## 1. Triage（数秒・無言）

上から順に判定し、最初に当たったものに従う。

1. **聞けない・聞くなと言われた・もう聞いた** → Skip（下記）。明示要求より優先する。
   - 非対話の実行（`claude -p`・cron・サブエージェント）
   - 「質問不要」「聞かずに」「急ぎ」「至急」「そのままで」と明示された
   - 同じタスクで既に triage した（同じ成果物・同じ問題への追加指示や続き、選んだ案の続行は同じタスク）
   - Codex へのレビュー/相談依頼・/workflows やサブエージェントの指定など進め方の指示は、新しい依頼にも続きにも付くので、Skip にも聞き返しにも使わない。残りの依頼本体で判定する
2. **明示要求**（「野心的に」「もっと上を」「深掘り」「ambitious」など、野心度を上げてほしいという依頼）→ 聞き返す。シグナルが弱くても、効きそうな軸で案を作ってよい。語の意味を聞いているだけ・否定しているだけなら明示要求ではない。
3. **Speed で足りる** → Skip。シグナル表に当たる要素があっても Skip が優先する。
   - typo / rename / 整形 / 1行修正、コマンド実行の依頼
   - 事実や概念の質問（「A と B の違いは？」「これは何？」）
   - 成果物の中身と形がユーザーの言葉で確定している（例:「--json を追加。項目は表と同じでいい」）
   - 個人的な短い文面（お祝い・お礼のメッセージなど）。Altitude は創作に効きにくい
4. **緊急**（本番障害、当日〜翌日の締切。明示の「急ぎ」は 1 で Skip 済み）:
   - 直す物が決まっている（障害・バグ）→ **後置き**。先に元の依頼の範囲で片付け（バグなら systematic-debugging に従い根本原因まで直す）、完了報告の末尾で §2 の形式の1問を出す。
   - 選択によって作る物の構成が変わる（資料・設計）→ 5 のシグナルがある時だけ先に聞く（無ければ Skip）。案は、ユーザーが確認する時間を残して締切までに終わる規模に絞る。
5. **シグナルがあり、上げた時に成果が大きく変わる** → 聞き返す:

| シグナル | 効く軸 |
|---|---|
| 成果物の名詞（資料・レポート・シート・スクリプト）だけで、それで何を起こしたいかが無い | Altitude |
| 会議・意思決定・報告に使う（会議があるなら Altitude の好機） | Altitude |
| 繰り返す仕事（毎週・毎月の手作業、同種の依頼）、個別インスタンスの修正（バグ1件・遅い API 1本） | Altitude（状態を保つ仕組みへ） |
| 要約済み・テンプレの数字・二次情報から始めている | Depth（生データから） |
| 品質を求めているのに方法が素人のまま（markdown 表で分析など） | Depth（プロの道具） |
| 通説・前提に依存（「原因は〜のはず」「〜な気がする」） | Depth（生データで反証を試みる） |
| 分析・予測・性能・最適化など正しさの判定が難しい仕事で、テストや実測といった外部の判定手段が依頼にも環境にも無い | Depth（外部の判定者） |
| 人を動かす仕事（説得・合意・採用・営業・組織運営など） | Range |

6. どれにも当たらない → Skip。

Skip は「聞き返さない」という意味で、依頼の水準を下げることではない。依頼文に含まれる指示（「野心的に」「深掘りして」など）はそのまま守り、同じタスクの続きなら前に選ばれた案の水準を引き継ぐ。明示要求があるのに聞けない時は、推奨案に当たる水準で質問せずに実行する。
hook に促されて skill を開いた場合でも、Skip と判定したら同じく何も言わずに進める。triage したことにも触れず、完了時に格上げを提案することもしない（通常の作業報告や、作業に必要な確認は普段どおり行う）。
迷ったら「選択肢を見せられてユーザーが得をするか」で決める。依頼固有の書き換え案が作れず汎用的な問いになるなら聞かない。

## 2. 聞き返し（1問だけ）

- 聞く前の軽い read-only 調査（3回程度のツール呼び出しまで）は、選択肢の文面や前提が中身次第で変わる時だけ行う（CSV の粒度、既存スクリプトや対象一覧の有無など）。重い作業は選ばれた後。
- 野心度以外の事実の曖昧さ（「今月」がどの月か、職種など）は、常識的な既定値で仮定し、質問文の末尾に括弧書き1文でまとめて明示する（ユーザーは「Other」で訂正できる）。質問を増やさない。
- 選択肢は **書き換え案2〜3個 + 最後に「そのまま」** の計3〜4個。AskUserQuestion は単一選択（multiSelect: false）で使う。
  - 先頭が推奨案で、ラベル末尾に「(Recommended)」を付ける。推奨はシグナルが最も強い軸の案。並ぶ時は、依頼のスコープに近く前提（アクセス・設定）が少ない方。
  - シグナルがある軸だけで案を作る（明示要求の時を除く）。同じ軸の段階違い（Altitude と Altitude 最大）でもよい。
  - 「そのまま」はラベルを文脈に合わせ、preview は元の依頼文にする。相談なら「そのまま相談に乗る」。明示要求なら「書き換えずに進める」（いつもの進め方で、できるだけ高く狙う）。後置きなら「ここで終える」で、preview は不要。
- **各案は、野心度の判断をもう一度ユーザーに求めずに着手できる依頼文にする。** 「何を起こしたいか」のようにユーザーしか知らない答えが要るなら、その候補自体を別々の案にするか、データから判定する依頼文にする。対象 URL の一覧のような入力データの不足は、選択後に §3 の「足りないもの」として伝えてよい。
- 各案の description には「何が変わるか」1行と、必要な前提（データ・権限・ツール）を短く書く。
- Claude Code では AskUserQuestion を使い、各案の `preview` に書き換え後の依頼文の全文を入れる（15行程度まで）。ユーザーが次回そのまま使える言い回しになる。質問文は依頼に即して書き、前置きの地の文を付けない（後置きの完了報告は別）。
- AskUserQuestion が無い環境では、同じ内容を番号付きで出し「番号で選んでください（そのままなら N）」で締める。
- 「1問だけ」は野心度の質問の数のこと。選択後に他の skill（brainstorming など）が行う要件確認や、必要な承認まで禁じるものではない。

書き換えの型（具体例は references/techniques.md）:
- **Altitude:** 「X を作る/直す」→「X で起こしたいこと Y を実現する。最も効く手段を選び、必要なら X 自体を置き換える」。核の問いは「これが終わった後、何が起きてほしい？」
- **Depth:** 第一人者ならやるが頼まれていないこと／出発点にする最も生の素材／使う手法と道具／自分たち以外で正しさを示すもの、の4点を入れた依頼文。性能・コスト・精度のように数値目標が自然な時は、現状より1桁以上良い非常識な目標を置く（10秒→5秒ではなく 200ms）。診断や相談で根拠の無い数値をでっち上げない。
- **Range:** 名詞を動詞にする（四半期レビュー =「忙しい人に因果の物語を信じさせ、不確実な中で30分で決めさせること」）。そこから必要な分野と、反対側から攻める red team を1つ選ぶ。

## 3. 選択後の実行

- **そのまま**: 通常どおり実行する。このタスクでは以後聞かない。
- **Altitude**: 人を介さず回り続ける仕組みにできるかを見る。必要な配管（データ取得経路、バージョンとコミットの対応、再現・検証環境）を先に揃える。繰り返し作業なら自動化を提案する（決定的な処理は CI の cron やスクリプト、判断を伴う処理は /schedule・/loop・hooks）。
- **Depth**: 語彙ではなく手法を切り替える（markdown 表 → DB・統計モデル・プロファイラ・ベンチマーク）。生データから始め、前提は再現を試みて反証する。「無理そう」でも分解して続け、高い目標に対する実測の到達度を報告する。正しさは自己評価ではなく外部の判定者（テスト、ベンチ、hold-out データ、Codex レビュー、実測）で示す。
- **Range**: 動詞化した目的から必要な分野を3〜5挙げ、各分野の人が**実際にやること**を実行する（独立していればサブエージェント並列）。「〜のように書く」ロールプレイにはしない。
- どの案でも、足りないもの（MCP 接続・データ・権限・実行環境・対象一覧）があれば着手前に一覧で伝える。

## 4. 他 skill との順序

- この triage を最初に行う。brainstorming / writing-plans / systematic-debugging / slide-deck / Artifact の quickstart / orchestrate-with-advisory などは、野心度が決まってから起動する（後置きの場合は通常どおり先に動かす）。
- brainstorming が続く時は、この1問をそこでの最初の質問として兼ねる。二重に聞かない。
- Skip した時は、元の依頼文どおり（同じタスクの続きなら選ばれた案の水準で）他の skill に進む。

## Anti-patterns

- 「どの軸にしますか？」のような汎用質問、野心度の質問を2つ以上、自由記述だけの質問
- 選ばれた後に、野心度の判断をもう一度求める選択肢
- ユーザーが選ぶ前に野心案のスコープで作業を始める
- Speed の依頼で聞き返して摩擦を増やす
- 「専門家として」と言いながら手法が変わっていない
- ロールプレイの文体だけ変えて中身が変わらない
