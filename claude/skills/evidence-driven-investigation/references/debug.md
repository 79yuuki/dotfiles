# アダプタ: デバッグ / 障害 / 根本原因

**このアダプタを読む時:** バグ・テスト失敗・クラッシュ・「遅い/落ちる/再現しない/たまに失敗する」・「なぜこの挙動になるか」の原因究明。
芯の7規律を前提に、デバッグ向けに具体化する。単一バグの体系的切り分け手順自体は systematic-debugging に従い、本アダプタはその上に複数仮説の並行探索と敵対的自己検証を足す。

## 仮説を機序で割る（規律1）

最初に目に付いた1つの原因に飛びつかない。**機序が異なる**仮説を 2〜3 本並べる。典型の軸:
- データ（不正値・境界・NULL・文字コード・サイズ）
- タイミング / 並行（競合・順序・初期化前参照・リトライ・キャッシュ整合）
- 設定 / 環境（バージョン差・feature flag・権限・依存の実バージョン）
- コードロジック（分岐・off-by-one・型混同 scalar vs array）
- 外部（上流 API・ネットワーク・時刻・ロケール）

各仮説に **「これが真なら何が観測されるはずか」= 反証条件** を付け（規律4）、最小再現でそれらを区別する。

## デバッグ特有の自己欺瞞（規律4）

- ログの**相関**を因果と断定する → 独立した経路で因果を確かめる
- 「たぶんこのコミット」を **bisect せず**断定する → `git bisect` 等で独立に特定
- 1回通ったのを「直った」と断定する → flaky は**複数サンプル**で発生確率を測る（単一実行は証拠にならない）
- 修正後: 必ず **別経路で再現を試みる** ＋ **正常系の対照**が壊れていないことを確認（規律: reproduced/resolved/inconclusive）

## 記録（規律6）

仮説・観測・**棄却理由**を出た瞬間に書く。棄却理由を残さないと、後で同じ行き止まりを理由なく再訪する（規律3違反）。根本原因に到達したら、再現手順と修正の因果を1か所に書き留める。
