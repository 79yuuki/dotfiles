# UX Walkthrough（メイン導線を人と一緒に通す）

製品のメイン導線（正常系）を、人とこのセッションが同じ画面を見ながら 1 操作ずつ通し、使い勝手を話して記録する。目的は 2 つ。人が一度も目を通していない導線をリリースしないこと。作った側でも気づける引っかかりを、出す前に拾うこと。

不具合を探す（異常な入力、権限、競合）のは exploratory-qa、機械で判定できる確認は playwright-e2e。ここでは、正常系を人の目で見ることだけを扱う。

## 1. 何を「確認済み」と数えるか

- 人が自分の目で、導線の最初から最後までを通して見たことだけを数える。このセッションだけの実行、E2E の成功、スクリーンショットの確認、サブエージェントの報告は数えない。
- 単位は「導線 × その導線のファイルの中身」。導線のファイルが変われば、未確認に戻る。
- 確認済みも見送りも、このセッションの判断では記録しない。人がその場で答えた時だけ記録する。
- 見送りは、一度は人が通して見た導線の、その後の変更にだけ使える。一度も見ていない導線は、通すしかない。
- 利用者調査の代わりにはならない。作った側は、初めて見る人の引っかかりを再現できない。記録にもそう書く。

## 2. リリースの前の点検

```bash
python3 <この skill のディレクトリ>/scripts/flows.py check     # リポジトリの直下で。見る版を変える時は --rev
```

導線の一覧は、リポジトリの `.github/main-flows.toml` に置く（書き方は [assets/main-flows.example.toml](assets/main-flows.example.toml)）。終了コード 1 は、未確認・変更あり・要修正の導線が残っている。2 は、一覧か記録が読めない。どちらも確認済みとして扱わない。1 の時は、3 節から先の手順で通す。一度見た導線の、その後の変更に限り、人が理由を付けて見送りを決められる。点検の結果は、完了やリリースの報告にそのまま書く。

- 点検を置く場所は、リポジトリごとに決めて指示書に書く。リリースの段が別にあるなら、その直前にまとめて通し、未確認が残っていれば出さない（PR では、結果を検証欄に書くだけでよい）。マージがそのまま本番に出るなら、導線に触れる PR を、マージの前に通す。
- 一覧は、見る版のコミットに入っているものを読む。手元で書きかけの一覧は使われない。導線の定義（利用者像・課題・入り口・paths）を変えた時も、その導線は未確認に戻る。
- 「変更あり」には、前に見た版から変わったファイルが出る。通し直すか、理由を付けて見送るかを、それを見て人が決める。
- 一覧が無いリポジトリでは、最初に一覧を人と作る。何がメイン導線かは人が決める。一覧は `.github/` に置くので、merge-gate では必ず人に回る。
- 見ているのは、そのリポジトリのファイルだけ。API や別のリポジトリの変更で画面のふるまいが変わる時は、点検が確認済みと言っていても通し直す。

## 3. 通す前に決めること

導線ごとに 4 つを書き出して、人に確かめる。一覧に書いてあれば、それを使う。

1. **誰として見るか。** 利用者像と、その人が知っていること・知らないこと（例: 初めて使う来店客。JPYC は持っているが、この画面は初見）。
2. **何をしようとしているか。** 金額や品名まで具体的に。
3. **操作列。** 主経路を先に書き出す。分かれ道は、どちらを通るかを先に決める。
4. **どの版の、どの環境か。** コミットと URL。通している間に環境を更新しない。

あわせて、テスト用のアカウントとデータを決め（本番を開かない。exploratory-qa の「始める前に」と同じ）、人の手が要る操作（4 節）を先に伝える。1 回に通すのは 1〜2 本にする。

## 4. ブラウザ

- **人が普段使っているブラウザを、人が見ている前で操作する。** 新しいタブを開いて使い、人が開いているタブには触らない。
- **操作するのはこのセッションだけ。** サブエージェントに渡さない。
- 接続は Claude in Chrome（拡張）を使う。最初に接続先を確かめ、それが普段使いのブラウザかを人に聞く。Chrome と Edge 以外（Brave、Arc など）は公式の説明が食い違っているので、最初の 1 操作で動くことを確かめる。つながらない時は、黙って別のブラウザ（同梱の Chromium など）に替えず、人に伝えて選んでもらう。
- 始める前に人へ伝える。操作中のタブに見えているものは、スクリーンショットとしてこの会話に入る。見せたくないものは別のウィンドウに移してもらう。
- **次の操作は、人が自分の手で行う。** このセッションは直前と直後の画面を読む。テスト環境でも同じにする。
  - ログイン、パスキー、生体認証
  - アカウントの作成
  - カード番号や本人確認の情報の入力
  - 支払い・送金・返金・引き出しの確定
  - CAPTCHA、ブラウザのダイアログ（alert / confirm）
- 話している間に接続が切れることがある。切れたら `/chrome` で再接続する。
- 録画（GIF）は既定で残さない。ログイン後の画面の情報まで写る。

## 5. 進行の決まり

最初に人へ伝える。進行はこのセッションが預かる。

- **通している間は「何が起きたか、どう感じたか、なぜ引っかかるか」まで話す。** 直し方の議論は、通し終えてからまとめて行う。その場で始めると、導線の後半を見ないまま時間が尽きる。思いついた直し方は 1 行で控えて先へ進む。
- **いまの作りを弁護しない。** このセッションも、コードの事情を知っているからといって説明に回らない。
- **引っかかっても止めない。** 控えて、通ったものとして最後まで進む。実際に先の画面へ進めなかった時は、そこから先は見ていない。確認済みにせず、直ってからもう一度通す。

## 6. 1 操作の進め方

1 操作は、利用者にとっての 1 つの行為（1 回のタップ、1 区画の入力から「次へ」まで）。

1. **新しい画面では、操作の前に人に聞く。** スクリーンショットを見せて、「この利用者は、次に何をすればよいか分かると思いますか」。ボタンの名前や正解を先に言わない。
2. **1 つだけ操作する。** 何をするかを 1 行で言ってから行う。人の手番（4 節）は、頼んで待つ。
3. **操作の後、人に聞く（AskUserQuestion）。** 「うまくいきました」と言う前に聞く。問いは「いまの操作が通ったことと、目的に近づいていることが、画面から分かりますか」。選択肢は「分かる（次へ）／分かるが気になる点がある／分からない・引っかかる／もう一度見る」で、メモを書けるようにする。人の言葉は言い直さずに控える。
4. **その後で、自分の観察を出す。** 多くて 3 個、根拠（画面のどこの何が、利用者像の何とずれるか）を付ける。良かった点も出す。コンソールのエラーと失敗したリクエストがあれば添える。画面の種類ごとの観点は [references/viewpoints.md](references/viewpoints.md)。
5. **控える（7 節）。** 問題が無ければ「通過」とだけ書く。

引っかかった操作だけ、どこで崩れたかを 4 つに切り分ける。利用者はそれをやろうと思うか。その操作が在ると気づくか。操作と目的が結びつくか。操作の後、進んだことが分かるか。

## 7. 控え方

- 種類は 5 つ。引っかかり（問題の候補）、直し方の案、仕様や設計の穴、操作列の誤り、良かった点。
- 引っかかりは、仮説の形で書く。「（利用者像）は〜しないかもしれない。〜を知らないから」。
- 人が「仕事でなければ、ここでやめていた」と感じた所は、切り抜ける前に控える。
- 「利用者はこの言葉を知っているはず」「よくある操作だから分かるはず」に頼った通過は、通過にせず控える。
- 深刻度は 0〜4 で、人が付ける。4 は出す前に直す。3 は優先して直す。2 は優先度が低い。1 は見た目だけ。0 は問題ではない。頻度・影響・繰り返し起きるかで考える。2 人で付けた値は目安として扱う。

## 8. 通し終えたら

1. **控えを人に見せ、深刻度の高い順に直し方を話す。** 直し方の議論はここで行う。
2. **結果を記録する。**

   ```bash
   python3 <この skill のディレクトリ>/scripts/flows.py record <導線の id> --result seen --by "<見た人>" \
     --env "<URL>" --browser "<ブラウザ>" --findings <控えた件数>
   ```

   `seen` は、通して見て、出す前に直す問題が無い。`fix` は、深刻度 4 が残っている（直すと中身が変わるので、もう一度通す）。`waived` は、一度見た導線のその後の変更について、人が見送りを決めた（`--note` に理由）。デプロイ済みの環境を見た時は、`--rev` でそのコミットを名指しする。
3. **引っかかりを票にする。** 起票するかどうかは人が決める。票から記録へ、記録から票へたどれるようにする。
4. **PR やリリースの検証欄に 1 行書く**（finishing-a-development-branch）。どの導線を、どの版で、誰が見たか。
5. **学びを書き戻す。** プロジェクト固有のこと（アカウント、環境の癖、導線の一覧）はプロジェクト側へ、どのプロジェクトにも当てはまることはこの skill の Gotchas へ。

## 報告の形

```markdown
## メイン導線の確認: <導線の名前>
- 見た人 / 日付 / 版（コミット）/ 環境 / ブラウザ:
- 誰として / 何をしようとして:
- 結果: 確認済み / 要修正 / 見送り（理由）
- 操作: N 個のうち、通過 N、引っかかり N

| # | 操作 | 種類 | 控え（人の言葉はそのまま） | 深刻度 | 票 |
|---|---|---|---|---|---|

- 良かった点:
- 確かめていないこと（通らなかった分かれ道、見ていない端末や画面幅）:
- これは利用者調査の代わりではない。作った側の 2 人が見た結果。
```

## Gotchas

- ブラウザの操作をサブエージェントに任せたら、ユーザーのブラウザが落ちた。
- 導線が 8 本あるリポジトリの過去 30 日を数えたら、97 回のマージのうち 57 回が、どれかの導線のファイルに触れていた。点検をマージのたびに強制すると、毎日通し直すことになる。リリースの直前にまとめる。

## 関連 skill

- exploratory-qa: 異常な入力や権限で不具合を探す。QA シートを人と 1 手順ずつ進める
- playwright-e2e: 機械で判定できる確認を spec にする
- ui-design-system / ui-accessibility-design: 見つけた引っかかりの直し方を設計する
- finishing-a-development-branch: PR の検証欄
- merge-gate: 人が diff を読まずにマージしてよいかの判定。導線の一覧の変更は必ず人に回る

## 出典

進め方は次の資料に基づく。細かい観点の出典は references/viewpoints.md。

- 1 操作ごとの 2 つの問いと、進行の決まり（その場で設計しない、弁護しない）: Spencer, "The Streamlined Cognitive Walkthrough Method" (CHI 2000)
- 引っかかった操作を切り分ける 4 つの問い: Wharton, Rieman, Lewis, Polson, "The Cognitive Walkthrough Method: A Practitioner's Guide" (1994)
- 画面ごとに止まる、失敗しても最後まで通す: https://www.nngroup.com/articles/cognitive-walkthrough-workshop/
- 深刻度 0〜4: https://www.nngroup.com/articles/how-to-rate-the-severity-of-usability-problems/
- 作った側は初見を再現できない: https://www.nngroup.com/articles/dogfooding/
- 人の操作に残すもの、接続と許可: https://code.claude.com/docs/en/chrome 、 https://support.claude.com/en/articles/12902446-claude-in-chrome-permissions-guide
- 「責任者が自分で通せなければ出さない」という関門の前例: 英国政府の旧 Digital by Default Service Standard（"Test the service from beginning to end with the minister responsible for it."）。導線ごとの台帳は、この skill 独自の作り。
