# Exploratory QA（探索的テスト）

動いているアプリを実際に操作して、テストケースに無い不具合と使いにくさを見つける。機械で判定できる確認は E2E に任せ（playwright-e2e）、ここでは機能をまたぐ組み合わせと、人の目が要る合否を扱う。

プロジェクト固有の前提（アカウント、環境の癖、過去に回して分かったこと）はプロジェクト側の skill か docs に置く。この skill には、どのプロジェクトでも同じ進め方だけを書く。

## 1. モードを決める

| モード | 使う場面 | ブラウザ | 合否を付ける人 |
|---|---|---|---|
| 人と一緒に回す | 人のアカウント・鍵・認証が要る。見た目や使い勝手の判断が要る。ユーザーが「一緒に」と言った | ユーザーのブラウザ。操作はこのセッション、認証はユーザー | ユーザー |
| 自走 | 検証環境が隔離されていて、テスト用アカウントだけで完結する | Playwright 同梱の Chromium | 裏どりを終えたこのセッション（6 節） |

迷ったら「人と一緒に回す」を選ぶ。合否の持ち主が人の時に、全部を自動で回して結果だけ書く進め方はしない。

## 2. 始める前に

1. **触る環境を固定する。** 検証環境の URL とテスト用アカウントを書き出し、本番を開かない。データを作る・変える操作をするので、ここを曖昧にしたまま始めない。
   - 削除・キャンセル・返金・権限の変更は、この回に自分が作った対象にだけ行う。名前が似ているだけの既存のデータには行わない。
   - 作るデータには、実行ごとに一意な値（メールアドレス、注文の名前）を入れる。後で「自分が作ったもの」と見分けるため。
2. **仕様を決めた記録を先に読む。** 合否の基準は記録（仕様書、決定の記録、チケット）で、いまの画面の動きではない。記録が無い所で食い違いに気づいたら、不合格ではなく「問題候補」として出し、仕様の確認に回す。
3. **対象に手段を付ける。** 機械で判定できる（E2E）／一緒にブラウザで見る／人の鍵や操作が要る／デプロイ待ち／仕様の確認、のどれか。
4. **人の手が要る操作を先に書き出し、まとめて頼む。** ログイン・送金・承認の待ちが、いちばん時間を食う。
5. **順番は「影響 × 起きやすさ」で決める。** 影響が大きいのは、お金・権限・取り消せない操作・止まると先へ進めない画面。起きやすいのは、今回変えた所と、過去に不具合が出た所。
6. **環境の状態を見る。** 残高・在庫・前回の実行の残りなど、結果を変える前提を確かめる。

## 3. 観点はツアーで選ぶ

画面ごとではなく「何を確かめたいか」でシナリオを分ける。1 本のツアーが画面をまたいで動くので、機能どうしが絡む不具合が見つかる。

| ツアー | やること |
|---|---|
| ガイドブック | 説明書どおりに使う |
| FedEx | 1 件のデータを、登録から最後の出力まで追う |
| 反社会的 | わざと逆のことや、間違った順番の操作をする |
| 強迫観念 | 同じ操作を何度も繰り返す（二度押し、再送、再読み込み） |
| 雨天中止 | 途中でやめる、キャンセルする、戻る、閉じる |
| カウチポテト | 既定値のまま、空欄のまま進める |
| タクシー通行止め | 権限が無い状態で、すべての経路が止まるかを見る |

入力値・状態・環境・競合の細かい観点は、test-quality の `references/abnormal-cases.md` を使う。

機械で安く拾えるものは、どのツアーにも混ぜる。主要な画面では、操作して状態を作った後にアクセシビリティの自動検査（axe）を走らせる。コンソールのエラーと失敗したリクエストは、画面が正常に見えても毎回残す。自動検査はキーボード操作とフォーカスの問題をほとんど拾えないので、キーボードだけで操作するツアーを別に回す。

## 4. 1 ラウンドの流れ

1. **チャーターを 1 文で書く。** 「（対象）を、（手段・アカウント・データ）で探索し、（知りたいこと）を見つける」。ツアーは動き方、チャーターは何を見つけたいか。
2. ツアーを 2〜4 本選び、ツアーごとにシナリオを書く。シナリオは、画面で行う操作の手順と、合格に見えるもの。シナリオごとに、手数か時間の上限を先に決める。
3. 操作する。証跡として、操作の前・途中・後のスクリーンショット、コンソールとネットワークの記録、実際に入れた値と返ってきた値を残す。操作する側が書くのは観察（見たこと）だけにし、合否は書かない。目的の操作が最後まで通っても、途中で見えた異常（想定と違う文言、表示の崩れ、遅さ、エラー）は別に書き出す。
4. 裏どりする（6 節）。
5. 「確かめていないこと」を書き出す。次のラウンドのシナリオはここから作る。

続けるかどうかは、時間ではなく「確かめていないこと」が残っているかで決める。新しい発見が出ないことは、探索が尽きた証拠にならない。操作する側は、深い所に届く前に探索をやめることがある。残りが人の手・デプロイ・仕様の確認だけになったら止めて報告し、止めた理由（上限に達した／確かめていないことが無くなった／人待ち）と、かかった規模（ラウンド数、時間）を書く。

## 5. 人と一緒に回すとき

手を動かす前に、1 手順ごとに次の 4 つを短く見せる。

- **確かめること**: 画面のどこの何かを、普通の言葉で書く。ID や略語だけで書かない。
- **なぜ**: 仕様の出典。
- **手順**: 誰が何をするか。人の操作は太字にする。
- **合格に見えるもの**: 画面の文言・状態。初めて出る用語は 1 行で説明し、言葉で伝わらなければスクリーンショットで見せる。

操作したら、AskUserQuestion で 1 問ずつ聞く。選択肢は「合格／不合格／要確認／もう一度」で、メモを書けるようにする。**合否は、ユーザーが確かめてから付ける。**

- 開く・入力する・押すはこのセッションが行う。パスワード・パスキー・生体認証・送金はユーザーが行う。
- 人の操作を待つ場面では、PushNotification が使えるなら呼ぶ。
- 仕様の判断を聞く時は、いまの画面・前提・選択肢ごとに画面がどう変わるかを添えて、1 問ずつ聞く。選択肢だけでは判断できない。
- 使いにくさや文言の違和感は、合否と別に控える。区切りでまとめて見せる。
- 聞くのは、合否と仕様の判断だけにする。画面を開く、スクリーンショットを撮る、状態を読むといった操作は、聞かずに進める。

## 6. 合否を付ける前の裏どり

画面を操作した側の報告だけで「不合格」「不具合」にしない。操作した側は、見えている画面の外のことが分からない。

- **画面以外の手がかりで確かめる。** API の応答、サーバーのログ、DB やチェーンの状態、コード、仕様の記録。操作する役と裏どりする役は、分けられる時は分ける（隔離したブラウザの操作をサブエージェントに任せ、このセッションが裏どりする）。分けられない時は、操作を終えてから、画面を見ずにこれらの手がかりだけで確かめ直す。どちらの場合も、画面の見た目だけを根拠にした「不合格」は付けない。
- **「合格」も裏どりする。** 成功の表示が出ただけ、既に在った行を見ただけ、見た目は正しいが金額・権限・状態が違う、という合格の見逃しが起きる。この回に作ったデータの一意な値を、一覧や API で読み戻して確かめる。エラーの後にやり直して通った時は、最初の失敗を問題として残す。
- **期待された拒否は、問題にしない。** 権限が無い時の拒否、入力の誤りの拒否、回数の制限は、仕様どおりなら注記に回す。サーバー側のエラー（5xx）は、この扱いにしない。
- **再現を 2 回確かめる。** 状態を戻して、独立にもう一度。
- **同じ原因は 1 件に束ねる。** 起票は原因ごとにする。
- **何と食い違うかを書く。** 問題ごとに、食い違う相手を 1 つ書く。仕様の記録／前の版の動き／同じ製品の別の箇所／利用者の目的／法令や標準。仕様の記録と食い違うものだけを不合格にし、それ以外は問題候補として出す。
- **判定は 3 値にする。** 合格／不合格／要確認。要確認には、何が確かめられなかったか（人の鍵、外部サービス、環境）を書く。要確認を、合格にも不合格にも数えない。
- **重要度を付ける。** 高は、お金・権限・データが壊れる、または先へ進めない。中は、遠回りで済む。低は、表示と文言。

## 7. ブラウザの扱い

- **人のブラウザ（ログイン済みのプロファイル）の操作を、サブエージェントに任せない。** このセッションが直接行う。
- 自走は、Playwright 同梱の Chromium を隔離したプロファイルで使う。サブエージェントに任せてよいのは、この隔離したブラウザだけ。
- 繰り返す操作は一時 spec にする。置き場所は、リポジトリ内の gitignore 済みのディレクトリ。一時ディレクトリ（`/tmp`、scratchpad）に置くと消える。QA を終えたら、残す価値のあるものを E2E に昇格させる（playwright-e2e）。

## 8. 区切りでやること

1. **記録する。** プロジェクトが決めた場所（QA シート、チケット、PR）に、結果・実施日・証跡・不具合の URL を書く。
2. **「確かめていないこと」を書き出す。** 未実施の項目とその理由、手段が無くて見ていない観点。
3. **拾った UI/UX の改善点を一覧にする。** 起票するかどうかは、ユーザーと決める。
4. **学びを書き戻す。** 効く順に、テスト ＞ lint・CI ＞ hook ＞ skill ＞ 指示書 ＞ メモ。同じ詰まりが 2 回起きたら、注意書きを足す前に、機械で止められないかを考える。プロジェクト固有の学びはプロジェクト側へ、どのプロジェクトにも当てはまる学びはこの skill の Gotchas へ書く。
5. **この skill を変えた時は、出来を測り直す。** 既知の不具合を仕込んだ環境で回し、見つけた数と、誤って問題にした数を、前回と比べる。
6. **人に渡す時・セッションを切る時。** 渡す項目から、その人が持っていない鍵や権限が要るものを外すか、先に書く。環境に残したもの（テストデータ、開いたトンネル、作ったアカウントや鍵）を書き出す。

## 報告の形

```markdown
## Exploratory QA report
- 対象と環境: （URL、ビルドまたはコミット、アカウントの種類）
- 回したツアー: （ツアー名とシナリオの数）
- チャーター: （対象、手段、知りたいこと）
- 見つけた問題: （原因ごとに 1 行。重要度、何と食い違うか、再現手順、裏どりに使った手がかり）
- 問題候補: （仕様の記録が無い食い違い）
- 仕様どおりと確かめたこと: （仕様の出典ごと）
- 要確認: （何が確かめられなかったか）
- 確かめていないこと: （未実施の項目と理由）
- 止めた理由と規模: （ラウンド数、時間）
- UI/UX の改善点: （合否とは別）
```

再現手順は、操作の記録から書く。覚えている内容や推測で補わない。期待と実際、環境、証拠を揃え、再生できる一時 spec があれば添える。

## Gotchas

- 全部を自動で回して結果だけ書いたら、記録の誤記と、再現しない不具合の起票が混ざった。ユーザーは「全自動だと心配」と方針を変えた。
- ID や略語だけで説明したら、ユーザーは何の話か分からず止まった。
- ブラウザの操作をサブエージェントに任せたら、ユーザーのブラウザが落ちた。
- 一時 spec を一時ディレクトリに置いたら、設定ごと消えた。
- 操作した側の読み違いが何度もあった。空の欄を不具合と報告したが仕様どおりだった。似た ID を取り違えた。金額の桁を読み違えた。

## 関連 skill

- ux-walkthrough: 正常系のメイン導線を、人と 1 操作ずつ通して UI/UX を見る。リリース前に、人が見ていない導線を残さない
- playwright-e2e: 機械で判定できる確認を spec にする。E2E の書き方の決まり
- test-quality: 異常系の観点。テストが壊れを見つけられるかの検品
- create-verification-skill: プロジェクトのアプリを起動して操作する手順を、プロジェクト側の skill として残す
- evidence-driven-investigation: 見つけた不具合の原因を調べる
- merge-gate: 人が diff を読まずにマージしてよいかの判定
