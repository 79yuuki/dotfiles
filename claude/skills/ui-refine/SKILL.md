# UI Refine（仕様は変えずに、間違えずに使える画面にする）

**人は画面の文を読まない、を出発点にする。本文を全部隠しても、見出し・ボタン・図・状態の表示だけで操作できる画面にする。説明を足さず、構造・ラベル・図・順番・既定値・制約で伝える。削った説明は行き先を決める。できること・状態・流れ（仕様）は勝手に変えない。**

流れは、柵を立てる → 棚卸し → 見立て → 直す方針 → 確かめる → 導線ごとに PR。見立てと方針だけを頼まれた時は 4 節で止めて返す。

## 0. プロジェクトの設定を読む

プロジェクト固有のこと（仕様の正本の場所、触ってはいけない文言、ブランドの文書、導線の一覧、用語集）は、この skill に書かない。プロジェクトに置く設定ファイルから読む。

- 場所は、CLAUDE.md や AGENTS.md に書かれていればそこ。書かれていなければ `docs/ui-refine.md`。
- 無い時は [references/project-config-template.md](references/project-config-template.md) を写して作り、リポジトリから分かる所（仕様の文書、E2E の場所、導線）だけを埋める。「外部に事前共有した画面の文言」と「規約・法定の表示」は人に聞いて埋める。
- ある時も、この 2 つの欄を確かめる。空欄や「確認中」は未確認として扱う（無い時は「なし」と書いてもらう）。未確認のあいだは文言に手を付けない（見立てと、配置の案までは進めてよい）。
- 人にすぐ聞けない作業者（別のワーカーなど）は、欄に「確認中」と書いて進める。確認中のあいだに文言を直してよいのは、外部に共有した範囲が仕様の正本や記録（共有した画面の一覧、影響の判定）から読み取れて、その画面が範囲の外だと根拠を挙げて言える時の、A の言い換えだけ。根拠と、した言い換えを PR に書き、人が確かめる。読み取れなければ文言に手を付けない。
- 設定ファイルや、それが指す仕様の正本とこの skill が食い違ったら、設定ファイルと仕様に従う。この skill の定番（ボタンに括弧書きを付けない、など）に沿う直しは、聞く案に回す。

## 1. 柵を立てる（変えないものを先に並べる）

ここで言う仕様は 3 つ。できること（操作の種類と、その結果）、状態（画面とデータの状態と、その移り変わり）、流れ（段の順番、分かれ道、先へ進む条件）。

- 設定ファイルにある仕様の正本と E2E テストを、「変えないもの」として一覧にする。
- 画面を通すテスト（E2E）が無い・止まっている時は、部品のテストと型チェックを柵にする。撮影は手元の開発サーバーで、作り物の応答（Playwright の `page.route`）を返して行う（本物の API と個人情報は使わない）。E2E が無いことと、作り物の応答で撮ったことを PR に書く。
- 仕様の正本が見せ方まで決めていることがある（文言の表、図、色、強調、並び、「隠さない」「読みにくくしない」のような見せ方の決まり）。先にそれを探し、見つけたら柵に入れる。決められた文言は C と同じに扱う。
- 変えてよいのは、仕様が決めていない見せ方だけ。配置、強弱、同じ画面の中での順番と区画の組み方、部品、図、文の長さと言い回し、余白と色。
- 次は仕様の変更になる。直さずに、案として人に聞く。
  - 画面を分ける・まとめる、段の順番を変える
  - 先へ進む条件（チェックの必須、押せない条件など）を足す・変える・外す
  - 既定で選ばれている物を変える、操作を足す・消す
  - 金額・状態・選択肢などの情報を画面から消す、2 段目に隠す（説明文を削るのは、下の文言の分類に従う。まれにしか要らない補足を 2 段目に移すのはよい）
- 文言は 3 つに分ける。説明文を削るのも文言の変更として分ける（削ると伝わる事実が減るなら B）。迷ったら B、外部への共有が「確認中」「不明」の画面は C として扱う。

  | 分類 | 例 | 扱い |
  |---|---|---|
  | A 意味を変えない言い換え・削除 | 同じことの繰り返しを消す、「〜することができます」→「〜できます」、ボタン名を押した結果と同じ動詞にする（「払い戻しますか？」の「はい」→「払い戻す」） | 直してよい |
  | B 意味が変わる | 条件・結果・約束の範囲が変わる、用語を別の語に替える、名前で新しいことを約束する（「いいえ」→「やめて前の画面に戻る」） | 直さずに聞く |
  | C 外部に事前共有した画面の文言、規約・法定の表示 | 審査先に出した画面の文言、手数料や取消の条件の表示 | 触らない。法定の表示は置き場所や大きさにも決まりがあることがあるので、位置・大きさ・見えやすさも変えない。直したい時は聞く |

- B の文言と、仕様の文の書き換え（見せ方の決まり、文言の表、仕様と画面の食い違いの解消）は、聞く案に並べるだけでなく、PR ごとに仕様の書き換えの提案（前の文・後の文・理由）として出してよい。決めるのは人（設定ファイルの「決める人」）。決まるまで画面の文言は変えない。C は聞くだけにする。
- 直すうちに柵に触れそうになったら、そこで止めて人に聞く。

## 2. 棚卸し（全部の画面と状態を撮る）

- 設定ファイルの導線ごとに、すべての画面と状態を撮る。状態は、初め、入力中、エラー、処理中、完了、押せない状態、空、値が長い・大きい（最大の金額、長い名前）。
- 状態が多い画面（1 つの区画だけで十数の状態がある、など）は、全部の代わりに代表を撮る。何も済んでいない（初め）、途中（いま取りかかる段がある）、全部済み、エラー・読み込みの失敗、値が長い・大きい、取り消せない操作の直前。選んだ状態と、撮らなかった状態を PR に書く。
- 幅はスマホ（375 と 320）と PC。スクロールが要る画面は、ページ全体を頭から撮る（Playwright の `fullPage`）。画像の名前は `<導線>-<画面>-<状態>-<幅>.png` に揃える。
- 撮る時に、説明文の文字数と主な操作の数を数えておく（[references/evaluation.md](references/evaluation.md) の 3 節）。数える範囲は導線の本文に絞る（左のメニューやヘッダーを入れない）。直した後と比べる基準になる。
- 撮った画像は自分の目で見る。DOM やコードだけで見立てない。
- 隔離したブラウザで、テスト用のデータだけで撮る。本物の個人情報や鍵が写ったら消して撮り直す。

## 3. 見立て

1. **最初に、読まない前提で確かめる。** 本文の文字を全部隠した画面（[references/evaluation.md](references/evaluation.md) の 3 節の `hide: true`）を撮り、見出し・ボタン・図・アイコン・状態の表示だけでタスクができるかを、白紙の AI に試させる（同じ 1 節）。できない所が、いちばん大きい直しどころになる。そこは文を足さず、図・構造・状態の表示で伝える形に作り直す。白紙の AI に試させられない時は、隠した画像を自分で見て、何が伝わらないかを書き、白紙の AI での確かめは 5 節に回す。
2. 画面ごとに「誰が・何のために・この画面で何を決めるか」を 1 行で書く。続けて、機能 → 便益 → 価値 → 体験 を 1 行ずつ書く（[references/principles.md](references/principles.md)）。この 1 行に効いていない要素が、削る候補になる。
3. 3 つのものさしで点検する。
   - 発見できる・予測できる・学習できる、と悪い画面を見つける 7 つの問い: [references/principles.md](references/principles.md)
   - 誤操作を防ぐ定番: [references/heuristics.md](references/heuristics.md)
   - 説明臭さと AI 感: [references/ai-smell.md](references/ai-smell.md)。日本語の文は [references/writing-ja.md](references/writing-ja.md)
4. 指摘ごとに、場所（どの要素か）、何が起きる・起きそうか、当たる問いや定番、重さ、画面で確かめた事実か推測か、を書く。
5. 重さは 3 段。重い順に直す。
   - **誤操作**: 取り消せない操作、お金、データの消失、違う選択肢を選ぶことにつながる。読み違えると損をする所が分かりにくいのもここ。
   - **迷う**: 止まる、読み返す、次に押す物が見つからない、押すと何が起きるか分からない。
   - **見た目だけ**: 操作に影響しない（揃っていない、理由の無い装飾）。同じ導線の PR で安く直せる時だけ入れる。

見立ての表の形:

| # | 画面・要素 | 何が起きる・起きそうか | 当たる問い・定番 | 重さ | 事実／推測 |
|---|---|---|---|---|---|

行は重さの順に並べ、同じ重さの中は画面の上から並べる。表の後に、良かった点（直すと崩れる所）を書く。

## 4. 直す方針

中心の規則は 3 つ。

**説明を足さない。構造と図で伝える。** 分かりにくい所には、次の順に手を考える。上の手で済めば、下の手は使わない。

1. **消す**: 同じことの繰り返し、挨拶や前置き、画面を見れば分かること。
2. **ラベルに入れる**: 見出しを問いの形に、ボタンを結果の分かる動詞に、選択肢に中身の分かる名前を付ける。
3. **図と状態の表示で見せる**: 関係・流れ・手順・状態の違いは、文ではなく図で見せる（[references/principles.md](references/principles.md) の「図で見せる」）。手順の進み具合はステッパーやチェックの列、比べる話は左右に並べた図にする。図には見出しか代替テキストを付け、色だけに頼らない。図の中身は仕様の事実だけにする（新しい約束をしない）。
4. **配置と順番で示す**: 確かめる情報を操作の前に置く。主な操作を 1 つだけ強くする（段のある画面では、いま取りかかる段の 1 つ。やることが全部済んだ画面では、強くする物は無くてよい）。操作は時間の順に並べる（戻る・やめるが先、進む・確定が後）。関係する物を近くに置く。
5. **既定値と制約を見える形にする**: すでにある既定値や押せない条件を、見て分かるようにする（押せない理由をボタンの隣に出す、など）。入力の自動整形のように受け付ける値が変わらないものは、見せ方として扱う。既定値や制約を新しく足す・変えるのは仕様の変更なので、1 節に従って聞く。
6. **必要な時に出す**: 補助の説明を、その状態の時だけ出す、または 2 段目（「くわしく見る」など）に移す。段は 2 段まで。入口は中身が分かるラベルにする。操作が出る・押せる条件と時は仕様なので、ここでは変えない。
7. **残す**: どうしても要る説明は、最短にして、関係する操作のすぐ隣に置く。

説明を新しく足すのは、1〜6 では伝わらないと示せた時だけにする。足したら、理由を PR に書く。

**文字の予算を守る。** 画面ごと・区画ごとに、最初に目に入る本文の上限を決める。既定の目安は区画ごとに 1〜2 行・40〜80 字（研究の裏付けがある数ではなく、設計の目標。設定ファイルで変えられる）。超える説明は 2 段目か、別のヘルプのページへ移す。区画ごとに数えて（[references/evaluation.md](references/evaluation.md) の 3 節の `root`）、前後と、予算を守れたかを報告する。

**削った説明の行き先を必ず決める。** 消して終わりにしない。削る文ごとに、次のどれかを書く。

| 行き先 | 使う時 |
|---|---|
| 不要 | 同じ内容が画面の別の所にある。挨拶・前置き |
| ラベル・ボタン名へ | 説明の要点が、見出しや操作の名前で言える |
| 配置へ | 「先に〜を確かめて」のような順番の説明 |
| 2 段目へ（くわしく見る、ヘルプ） | 一部の人だけが要る背景・理由・仕組み |
| その時だけ出す | エラーや、条件を満たしていない時の案内 |
| 外の文書へ（FAQ・規約） | 画面の操作に関係しない |

取り消せない結果やお金の損についての文は、2 段目に隠さない。最短にして、その操作のすぐ隣に 1 回だけ残す。文言の分類が B か C なら、言い換えも削除もせずに聞く。

ほかの直し方（主な操作を 1 つにする、確認は 1 回、ボタンは動作名、エラーの書き方）は [references/heuristics.md](references/heuristics.md)、文は [references/writing-ja.md](references/writing-ja.md)、AI 感は [references/ai-smell.md](references/ai-smell.md) にある。同じくらい正しい直し方が複数ある時は、設定ファイルのブランドの文書の言葉に合う方を選ぶ（[references/principles.md](references/principles.md) の BRAND・VALUE・FUNCTION）。

方針は指摘ごとに次の形で出す。表は 2 つに分ける。「そのまま直す」（仕様への影響が無く、文言が A か変えない）と「聞く案」（B・C の文言、仕様に触れるもの）。聞く案は、実装の前に人に見せる。人にすぐ聞けない作業者は、聞く案を直さずに一覧にしたまま、そのまま直せる物だけを先に進めてよい。聞く案は PR の本文と報告に並べ、人が決めた後に直す。画面ごとに、直した後の姿を上から順に書く（文字の見取り図でよい）。

| # | 直し方（前 → 後） | 使った手（1〜7） | 削る文と行き先 | 仕様への影響（なし／聞く） | 文言の分類（A／B／C） |
|---|---|---|---|---|---|

文を削らない行は「削る文と行き先」に「なし」と書く。「文言の分類」に「なし」と書くのは、文言を変えない行だけ（言い換えや、C の表示に触れる案には分類を付ける）。見立てと方針だけを返す時は、最後に、2 節の状態と幅のうち撮れていないものと、数えていない数を書く。

**控えめ版と大胆版を両方出す。** 文を 2 割減らす程度の控えめな直しでは、たいてい足りない。

- 控えめ版: 仕様にも B・C の文言にも触れない範囲（「そのまま直す」の表）だけで作る。
- 大胆版: 仕様の文の書き換え、図の追加、区画の組み直しまで含めて、読まない前提と文字の予算を満たす形で作る。仕様の書き換えは、前の文・後の文・理由を提案として出す（1 節。決めるのは人）。できること・状態・流れの変更と C の文言は、大胆版でも勝手に変えず、提案に留める。
- 大胆版は別のブランチで作る。前・控えめ版・大胆版を同じ状態・同じ幅で撮り、左右に並べて人に選んでもらう（[references/evaluation.md](references/evaluation.md) の 4 節）。マージするのは人が選んだ版だけで、仕様の書き換えが要る版は、その提案が決まるまでマージしない。

## 5. 確かめる（直した本人ではない目で）

1. **柵**: E2E がそのまま通る（E2E が無ければ、1 節で柵にした部品のテストと型チェック）。テストの期待している文言を直してよいのは、A の言い換えの時だけ。直した期待は PR に一覧で書く。
2. **数**: 説明文の文字数と主な操作の数を、前後で比べる（[references/evaluation.md](references/evaluation.md) の 3 節）。区画ごとに文字の予算を守れたかも書く。増えたら理由を書く。
3. **白紙の AI**: この skill も diff も読んでいない別の agent に、画面だけを見せてタスクをさせ、前後で比べる。合格の条件は、本文を隠した画面でも、見出し・ボタン・図・状態の表示だけでタスクができること（[references/evaluation.md](references/evaluation.md) の 1 節）。
4. **人**: ux-walkthrough の 9 節の recorder で前後を録画し、build-review で前後のページを作って人に見せる（[references/evaluation.md](references/evaluation.md) の 4 節）。良くなったかを決めるのは人。

AI の結果は甘めに出る（[references/evaluation.md](references/evaluation.md) の 2 節）。人が見るまで「分かりやすくなった」と言い切らない。

## 6. 導線ごとに PR

- 1 つの PR に 1 つの導線（支払う、残高を追加する、お店の登録、返金など）。別の導線の直しを混ぜない。
- 共通の部品を直して他の導線にも効く時は、効く導線を PR に書き、その導線も撮って前後を比べる。
- PR の本文に書くこと:
  - 何の導線か。変えていないもの（柵）と E2E の結果
  - 前後の画像（スマホと PC）と、ux-walkthrough のページの場所
  - 数の前後（説明文の文字数、主な操作の数、区画ごとの文字の予算）と、本文を隠した画面での結果
  - 控えめ版と大胆版を作った時は、並べた画像と、どちらを選んだか
  - 白紙の AI の結果（何回、何が通り、何が通らなかったか）
  - 文言の変更の一覧（A／B／C）と、削った説明の行き先
  - 人に聞いて決めたこと。まだ決まっていない聞く案と、仕様の書き換えの提案（前の文・後の文・理由）
  - 確かめていないこと（撮っていない状態や幅、人ではまだ見ていないこと）

## Gotchas

実際に踏んだ失敗だけを 1 行ずつ足す。

- 最初の試しの画面は、仕様書が文言・図・色・強調まで決めていた。文言を削る直しはすべて聞く案になり、そのまま直せる案は仕様が決めていない所の強弱と余白に限られた（その強弱の直しも、仕様の「読みにくくしない」に当たらないかを人に見せる必要が残った）。仕様の正本に見せ方の決まりがあるかを、見立ての前に探す。
- 渡されたスマホ幅の画像が、ページの途中から撮られていて、金額と操作の位置関係を確かめられなかった。頭から撮る。
- 実際の画面で数えたら、左のメニューやヘッダーの文字まで数えた。`root` で本文に絞る。
- `keep` に表のセルを入れたら、セルの中のボタンまで `keep` に数えた。道具を、操作を先に判定する形に直した。
- 縦に長い画面を 1 枚の画像で確かめ役の AI に渡したら、縮小されて文字が読めなかった。区切って渡す（[references/evaluation.md](references/evaluation.md) の 1 節）。
- 試しで `keep` を金額の一覧だけにしたら、枚数・公演日・規約の表示・取り消せない警告まで説明文として数え、隠した画面からも消えた。`keep` には値・C の表示・残す警告を全部入れる。

## 関連 skill

- exploratory-qa: 異常な入力や権限で不具合を探す
