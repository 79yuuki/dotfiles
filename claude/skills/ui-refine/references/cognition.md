# 人の認知に合わせる決まり

人は画面の文をあまり読まず、作業の途中の注意は届かず、同じ注意には慣れる。ここには、その調べ（出典つき）と、そこから出る画面の決まりを置く。見立て（SKILL.md 3 節）でものさしとして当て、直す方針（4 節）で使う。決まりを当てて直すことが仕様（できること・状態・流れ）や文言（A／B／C）に触れる時は、SKILL.md 1 節に従って聞く案にする。

目次: 1 調べて分かったこと / 2 一時的な知らせは一時的な部品で / 3 よい知らせは短く、注意は効く区切りに / 4 直前の操作をなぞらない / 5 縦の長さと文字の予算 / 6 外のサービスとの関係は知っている型で（型を使う前に法の柵に照らす） / 7 はじめての人と前に使った人 / 8 始める前に説明しない

## 1. 調べて分かったこと

番号は末尾の出典。「画面での使い方」に「推論」と書いた所は、出典がそこまでは言っていない（この skill の当てはめ）。

| 分かったこと | 画面での使い方 |
|---|---|
| 人は文をあまり読まない。1 ページの文字のうち読む時間があるのは多くて 28%、ふつうは 20% ほど（閲覧の記録からの推計、2008 年）［1］ | 読まない前提で作る（SKILL.md の出発点） |
| 広告のように見える囲みは、中身が大事でも飛ばされやすい［2］ | 色を塗った大きな箱に、読ませたいことを入れない（推論）。流し読みの確かめで、誰も覚えていない箱を探す |
| 一度に頭に置けるのは 4 まとまりほど［3］ | 1 画面で見る塊・決めることを絞る（推論） |
| 作業の途中に出た警告は、脳の反応が大きく下がる。作業の直後に出すと、警告だけに集中した時と同じくらい反応した［4］ | 注意は作業の切れ目に出す。お金を入れる前・残高ができた時・失敗の直後も切れ目として扱う（推論） |
| 同じ警告は慣れて見なくなる。見た目を変えると慣れにくい［5］ | 同じ注意を毎回同じ箱で出さない。2 回目は形を変える |
| 操作を止めて選ばせる警告は 79% が従い、操作を止めない受け身の警告は 13% だった（60 人。論文の考察の値。結果の節では、受け身の組は 10 人中 1 人）［6］ | 止める形は、どうしても伝える 1 つに使う。ほかを受け身で短くするのは推論 |
| 文で理解させる狙いは届かず、安全な選択を見た目で強く示したら、安全な側を選ぶ人が 3 割近く増えた［7］ | 推奨は塗りと位置で示す |
| 怖さを伝える時は、すること（効く対策）を添えると効く。1 回で済む行動だと特に［8］ | 注意には、することを 1 つ添える |
| 使う前の説明（チュートリアル）は、読んだ人と飛ばした人で成功率が変わらず（91% と 94%）、読んだ人のほうが難しく感じた［9］ | 始める前に説明しない（8 節） |
| 1 画面に 1 つのことから始める［10］［11］ | 1 画面で決めることは 1 つ |
| 伝える時機には型がある（設定の時・必要になった時・状況が変わった時・定期・常時・求められた時）［12］ | 「必要になった時」「状況が変わった時」に寄せる（推論） |
| 長く複雑な手続きは、注文をやめる理由になる（米国の通販で、注文をやめた理由として 17% が挙げた。2026-11-27 に確かめたページの値）［13］ | 縦の長さと段の数を予算で抑える（推論。5 節） |
| パスキーの指針は、作った後に「アカウントができました」をホームの画面に重ねて出すよう勧める［14］。作った後の確かめの画面は理解に役立つ［15］ | 作った直後の知らせは、重ねて出す部品（閉じられるモーダルなど）で短く出す。主な道の画面に残さないのは推論（2 節） |

## 2. 一時的な知らせは一時的な部品で

一時的な知らせとは、操作の結果（できました・保存しました・送りました）のこと。次へ進めば要らなくなる。

| 知らせの中身 | 部品 |
|---|---|
| 結果だけ | 短い知らせ（トースト）。1 行 |
| 作った直後など、作業の切れ目で 1 回だけ見てほしい結果 | 閉じられるモーダル。見出し 1 行と値 1 行まで（この skill の決まり。パスキーの指針［14］は、アカウントを見るボタンなども勧める）。× と Esc で閉じられ、ボタンを置くなら名前は押した結果どおり（「閉じる」） |
| 後でも要る状態（同期されている、など） | 小さい状態の札を画面に残す。段落は残さない |

- よい知らせの部品には、注意を入れない（3 節）。
- 主な道の画面のいちばん上に、知らせの箱や段落を残し続けない。主な操作が下へ押し出され、色の箱は読まれない（［2］）。
- 自動で消える知らせは、読み上げに伝わるようにする（WCAG 2.2 の 4.1.3 Status Messages、［16］）。消える前に読める時間も取る（止める・延ばす・閉じるまで残す、のどれかができる形。2.2.1 Timing Adjustable の考え方、［17］）。
- モーダルは、開いた時にフォーカスを移し、閉じたら元の場所へ戻す。
- 仕様との関係:
  - 段落を短い知らせに替えるのが見せ方の変更で済むのは、その結果が次の画面か状態の札で見え続ける時だけ。情報が画面から消えるなら聞く案。
  - モーダルは閉じる操作が 1 つ増えるので聞く案。モーダルのボタンで次の段へ進ませる形は、流れの変更なので聞く案。
  - 仕様が「モーダルで止めない」「常に出す」と決めていれば柵。

## 3. よい知らせは短く、注意は効く区切りに

- よい知らせの部品（トースト・モーダル・完了の見出し）は、見出し 1 行と値 1 行まで。注意をぶら下げない。完了の画面に記録として並べる値（金額・相手・日時・番号）は注意ではないので、この数に入れない。
- 注意が要る時は、効く区切りに、別に 1 回出す。効く区切りは、お金を入れる前、残高ができた時、失敗の直後。
- 注意は、何を失うかで置き場所を分ける。
  - その操作で失う注意（取り消せない支払い、消すと戻らない）は、その操作のすぐ隣に 1 回（SKILL.md 4 節）。
  - 持っている間に失う恐れの注意（鍵を失くすと残高に触れられない、など）は、失うと困る物（残高）ができた時に出す。鍵を作った時（よい知らせの時）ではない。
- 注意を別の画面や別の時へ移すのは聞く案。仕様が出す場所を決めていれば柵で、文言は A／B／C に従う。お金・取り消せないことの注意は、移す先が決まるまで元の場所から消さない。
- 注意の形は「何が起きるか 1 行＋すること 1 行」（［8］）。仕組みの説明は 2 段目へ。
- 同じ注意は、ふつう 1 回。2 回出すと決めた時（聞く案）は、違う区切り・違う形にする（［5］。試しでは、同じ形の繰り返しに流し読みの AI が気づいて飛ばした）。同じ画面で重ねない。

## 4. 直前の操作をなぞらない

- 利用者がいま入れた値・選んだ物を、同じ画面や次の画面で文にして繰り返さない（例:「お支払いを承認いただくと、5,000 円のお振込みのご案内に進みます」）。
- 確認の段で値を出すのはよい（[heuristics.md](heuristics.md) の 4 節。同じ値を同じ形式で）。違いは、値は値として 1 回出し（表の行・札）、文で語り直さないこと。
- これから起きることは、ボタン名（と、その下の 1 行）か、次の画面で、その時に出す。ボタンの下の補足と同じことを、別の区画でもう一度言わない。
- 手順の予告（①②③）を、手順が始まる前の画面に文で全部書かない。手順の画面で、ステッパーで出す。流れの全体を 1 つの図で見せるのはよい（[principles.md](principles.md) の「図で見せる」）。
- 見つけ方: 区画ごとに「この文は、利用者がこの画面か直前の画面でしたこと・見えている値・ボタン名・図で言えるか」を問う。
  - 言えるなら消す（行き先は「不要」）。
  - その文にしか無い事実のうち、押す前に知るべき事実（押した結果に関わる。別のタブで開く、このあと本人確認がある、など）は、消さずにボタン名かボタンの下の 1 行に残す。次の画面へ移せるのは、押した後に要る事実だけで、移すのは聞く案（文言は B）。

## 5. 縦の長さと文字の予算

- 主な端末はスマホ 375×667（設定ファイルで変えられる）。ブラウザの帯（アドレスバーなど）の分、実際に見える高さはもっと短い（端末とブラウザで違う。確かめていない）。主な操作は余裕を見て上に置き、低い高さ（既定 550）でももう一度測る（[evaluation.md](evaluation.md) の 3 節）。
- 主な道の画面は、スクロールする前の最初の画面に、その画面で決めることと主な操作が入るようにする。
- 入らない時の順番:
  1. 消す・なぞりを消す・一時的な知らせを外す・2 段目へ移す。
  2. 主な操作を下に固定する（仕様が配置を決めていなければ見せ方の変更）。取り消せない操作・お金の確定の画面で固定するなら、金額と取り消せない注意も一緒に固定する（確かめる情報を見ずに押せないように）。それができなければ固定しない。
  3. それでも入らない時に、画面を分ける（流れの変更なので聞く案）。
- 予算は主な道の画面（利用者が目的のために必ず通る画面）に当てる。組み込みの手順の画面のような長い設定の画面には、設定ファイルで別の予算を決めてよい。設定ファイルに無ければ、長い設定の画面には区画ごとの予算だけを当て、画面全体・縦の長さ・最初の画面（説明文と主な操作）は測って報告するだけにする。
- 予算の既定（設計の目標で、研究の裏付けがある数ではない。設定ファイルで変えられる）:

  | 測るもの | 既定の上限 |
  |---|---|
  | 画面の縦 | 2 画面分（375×667 なら 1,334px） |
  | 最初の画面の説明文 | 80 字 |
  | 画面全体の説明文 | 150 字 |
  | 区画ごとの説明文 | 1〜2 行・40〜80 字（SKILL.md 4 節） |

- 測り方: [evaluation.md](evaluation.md) の 3 節の `uiRefineText` の `viewports`・`primaryInFirstView`・`firstViewChars`。棚卸し（SKILL.md 2 節）で直す前を測り、前後と、予算を守れたかを報告する。

## 6. 外のサービスとの関係は知っている型で（型を使う前に法の柵に照らす）

流れの中に外のサービス（発行・決済・本人確認・銀行）が出てくると、利用者は「何と何がどうつながっているか」が分からずに止まる。関係は、利用者がもう知っている型と図で見せる。型の言い方は法の柵に触れやすいので、先に柵に照らす。

1. 関係を 1 行で書く。誰の画面で何をし、お金や情報がどこからどこへ動くか（仕様の事実だけ）。
2. 利用者が知っている型を探す。例: 支払いのアプリに銀行口座を連携して入金する、「Google でログイン」、カードを登録する。型の名前（連携・登録）と見た目（2 つのサービスを線でつなぐ、つながっている状態の札）を借りる。
3. 型が約束することを書き出し、仕様の事実と比べる（例: 銀行口座の連携なら「一度つなげば、次からその口座で入金できる」）。人は型から期待を丸ごと持ち込むので、型の中心の約束が事実に無いと確かめられたら、その型を使わない。事実か分からない時は、型を捨てずに「確かめること」として案に添える。
4. **型を使う前に、設定ファイルの「法の柵」に照らす。** 型の言い方・図の矢印・状態の札が、欄にある柵のどれかに触れないかを 1 つずつ確かめる。
   - 照らすのは欄にある柵だけ。欄に無い柵を自分で足して型を捨てない。柵が足りないと思ったら、その柵が要るかを聞く案に添える。
   - 柵に触れるのは、たいてい型の言い方の一部（「入金」「チャージ」「預ける」など）。型を捨てずに、その言い方だけを替える（替える言い方は 5 に従う）。
   - 欄が空・確認中の時は、型を使った案は聞く案の形まで。柵に関わる言い方（下の観点に当たる言い方）は作らず、提案の「後の文」には「柵が決まってから」と書く。人に聞く時の観点: 事業者が利用者の資産を持っているように読めないか（預かり）、申込・購入などが自社の画面で成立したように見えないか（取引の成立）、要る物を「不要」と言っていないか、登録や免許の無い業務をしているように読めないか。
5. 柵に触れる言い方（柵の「避ける言い方」に近い所）は、設定ファイルの法の柵の「使える言い方」からだけ選ぶ。合う言い方が無ければ作らず、聞く案に回す。柵に関わらない事実の文と、欄が「なし」の時は、言い方を案として作ってよい（B）。図は 2〜3 の箱と矢印で、どの画面で何をするか・お金がどこに入るかを見せる（[principles.md](principles.md) の「図で見せる」）。
6. 見立てで関係の分かりにくさを見つけたら、型を使う案を、聞く案として少なくとも 1 つ出す。3 で使わないと決めた型は除き、除いた型と、事実と比べて捨てた理由を書く（これが「黙って落とさない」こと。使える型が残らない時も同じ）。型を使わない案（図だけ）を並べるのはよい。型の名前を画面に入れるのは用語の変更（B）。名前を出さずに型の見た目だけを借りる時も、画面に無かった事実を図や文で足すなら B。仕様の書き換えの提案として、前の文・後の文・理由・照らした柵を並べる。迷う時は、型を使う案と使わない案を並べて聞いてよい。

## 7. はじめての人と前に使った人

端末の印で、最初に強くするボタンと並びを変える時の決まり。印を新しく作るのは動作の追加なので聞く案（仕様にあれば仕様に従う）。端末に印を保存してよいか（同意が要る地域があるか）は、法の柵として設定ファイルで確かめる（確かめていない）。

- 印は、アカウントを作る・ログインするのが成功した時だけ付ける。開いた・押しただけでは付けない。
- 表示だけに使う（どれを塗るか、並び）。認証・権限・金額の判断に使わない。サーバーへ送らない（localStorage など、通信のたびに送られない所に置く。cookie は使わない）。個人を特定する値・鍵・資格情報を入れない（真偽か日付だけ）。
- もう一方の道を隠さない。変えるのは強さ（塗り／枠）と順番だけ。
- 印が無い・読めない・書けない時（別の端末、データの消去、プライベートモード）は、はじめての人と同じ扱いになるだけ。エラーを出さない。
- 保存の仕組みを説明する文（「この端末に記録しています」など）を足さない。ボタン名と図で、どちらが自分の道か分かるようにする。
- 前に使った道で失敗した時（この端末にパスキーが無い、など）は、その場（失敗の直後）でもう一方の道を見せる。行き止まりにしない。新しくリンクやボタンを足すなら、操作の追加なので聞く案。
- 同じプロダクトの別の画面にも印があれば、名前・意味・消え方をそろえる。
- 確かめ: 流し読みの確かめ（[evaluation.md](evaluation.md) の 5 節）を、「はじめての人」と「この端末で前に使った人」の 2 つの役で回し、役ごとに q2（次に押す物）の合否（3 回のうち 2 回以上正しいか）を前後で比べる。

## 8. 始める前に説明しない

- 入口と、何かを作る前の画面には、その画面で決めることと、決めるのに要る 1 つだけを置く。仕組みの説明は 2 段目へ（［9］［12］）。注意は 3 節に従う（取り消せない・お金の注意は操作の隣に残す。別の画面・時へ移すのは聞く案）。
- 長い説明が残るなら、図とアイコンに置き換える（[principles.md](principles.md) の「図で見せる」）。
