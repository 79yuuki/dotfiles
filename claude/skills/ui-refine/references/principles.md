# 原則と、悪い画面の見つけ方・直し方

もとは、原 佑一「いいUIとは？初心者向けに事例をもとにUIデザインを分解」（Speaker Deck、2026-08-29）。三大原則は、スライドの中で主席クリエイター山幡さんの定義として紹介されたもの。

## いい UI とは

サービスの機能を、使う人の「いい体験」に変えられるもの。

## 三大原則

| 原則 | 意味 | 確かめる問い |
|---|---|---|
| 発見できる | 何をすればいいかが一目で分かる | 画面を開いてすぐ、主な操作を 1 つ指させるか |
| 予測できる | 押す前に、何が起きるかを想像できる | ボタンの名前だけで、押した後の結果を言えるか |
| 学習できる | 一度使えば、次から説明なしで使える | 同じ種類の画面（確認、選択、エラー）が同じ型か |

## 悪い画面を見つける 7 つの問い

1. 何を聞かれているか分かるか（見出しが問いや、その画面でやることになっているか）
2. 問いと答え方が結びついているか（長い文の後に「はい／いいえ」で答えさせていないか）
3. 使う人に聞き慣れない言葉が無いか（社内語、仕組みの言葉、長い正式名称）
4. いつ何をすればいいか想像できるか（今やることと、後でやることが混ざっていないか）
5. 主な操作が一目で分かるか（同じ強さのボタンが並んでいないか）
6. 見たい順に並んでいるか（確かめる情報が、操作より前にあるか）
7. その説明は、無くても伝わるか

## 直し方 6 つ

1. 問いと操作をセットで見せる。見出しが問い、選択肢がその答え。
2. アイコンで操作を想像させる。アイコンは 1 セットに揃え、絵文字で代用しない。
3. 必要な操作は必要な時に出す。この skill では、出す時を変えてよいのは補助の説明だけ。操作が出る・押せる条件と時は仕様なので変えない。画面を分けるのも流れの変更。どちらも案として聞く（SKILL.md の 1 節）。
4. 余分な説明を読ませない。
5. 確かめてから押せる順にする。金額などの確かめる情報が上、操作が下。
6. 操作は時間の順に右へ。戻る・やめるが左、進む・確定が右。縦に積む時の順番は、プロダクトの中で 1 つに揃える（学習できる）。

## 図で見せる

人は画面の文を読まない。関係・流れ・手順・状態の違いを文で説明している所は、図にできないかを先に考える。スライドの例 1 では、「カードを先に挿入してください」という文が、次の段の挿入の図になった。

| 文で説明しているもの | 図の形 | 例 |
|---|---|---|
| 流れ（A から B へ、B から C へ） | 左から右への矢印でつないだ箱 | お店のサイト → 決済サービス → お客さん |
| 手順と進み具合 | ステッパー、チェックの列（済み・いま・まだ） | 鍵をつくる ✓ → ドメインを登録（いまここ） → 組み込む |
| 状態や選択肢の違い | 左右に並べて比べる図。当てはまる側に印 | 「端末だけに保存」と「同期して保存」で、端末をなくした時に残る物 |
| 操作のしかた | 物と動きの絵 | カードを差し込む向きの図 |

描き方:

- プロジェクトのデザインシステムに部品（ステッパー、図の部品、アイコン）があれば、それを使う。無ければ、線とアイコンだけの単純な SVG にする。
- 図の文字は HTML の文字か SVG の `text` にし、画像の中に焼き込まない（読み上げ・翻訳・テストのため）。図には見出しか代替テキストを付ける。飾りのアイコンは代替テキストを空にする。
- 色だけで意味を伝えない。当てはまる側は、印の文字や形でも分かるようにする。
- 図の文字はラベル程度にする。図の中に説明の文を入れない。
- 1 つの図に 1 つの話。図の中身は仕様の事実だけにし、新しい約束をしない。図の文言も、SKILL.md 1 節の文言の分類（A／B／C）に当てる。

## 例 1: 給油機の支払い方法の画面（スライド 5〜8 枚）

**前**: 見出し「処理を選択して下さい」の下に長い文。「クレジット機能付き提携ポイントカードで決済を行う場合は『はい』を選択してください。他の決済の場合は『いいえ』を選択し、お支払方法選択画面で決済したいカードを先に挿入してください。」その下に「はい」「いいえ」。

**問題**: 何を聞かれているかが分かりづらい（問い 1）。問いと答え方が結びつかない（問い 2）。「クレジット機能付き提携ポイントカード」が聞き慣れない（問い 3）。いつ何をすればいいかが想像しづらい（問い 4）。

**後**: ① 見出し「お支払い方法を選んでください」と、アイコン付きの選択肢「提携カードで支払う」「その他のお支払い方法」。② 次の段で「利用するカードを挿入してください」と、挿入の図。

**削った説明の行き先**（この skill の見方）:

| 前の文 | 行き先 |
|---|---|
| 何を選ぶ画面か | 見出し（問いの形） |
| 「〜の場合は『はい』」 | 選択肢のラベル（「提携カードで支払う」） |
| 「カードを先に挿入して」 | 次の段の見出しと図（必要な時に出す） |

この skill で同じ直しをするなら、画面を 2 段に分けるのは流れの変更、「クレジット機能付き提携ポイントカード」を「提携カード」に縮めるのは用語の言い換え（意味が変わらないか確かめられなければ B）なので、どちらも案として人に聞く。

## 例 2: 券売機の画面（スライド 9〜12 枚）

**前**: 「[発券]ボタンが表示されましたら[発券]ボタンを押してください。」「[発券]ボタンを押してください。」の 2 文。青い「発券」と赤い「取消」が同じ強さで並ぶ。その下に小さく「投入金額・購入金額・おつり」。

**問題**: 説明は無くても伝わりそう（問い 7）。どちらが主な操作かが一目で分からない（問い 5）。見たい順が逆で、金額が下、ボタンが上にある（問い 6）。

**後**: 説明の 2 文を消す。金額 3 行を上に、その下に「取消」（枠線だけ・左）と「発券」（黒く塗る・右）。

**削った説明の行き先**: 2 文とも「不要」。ボタンが出ていること自体が「押せる」を伝え、塗りの強さが「どれを押すか」を伝える。「金額を確かめてから押す」は配置（上が金額、下が操作）に移った。

## 学習できるの例と注意（スライド 16 枚）

「発券しますか？ 取消／発券」と「この内容でいいですか？ 戻る／OK」のように、確認の画面を同じ型（問い、左に弱い操作、右に強い操作）に揃えると、一度で覚えられる。

ただし、スライドの「OK」はそのまま真似しない。ボタンは動作名にする（[heuristics.md](heuristics.md) の 2 節）。型を揃えるとは、問い・やめる（左）・確定（右、動作名）の並びを揃えること。

## BRAND・VALUE・FUNCTION（スライド 19〜21 枚）

- BRAND: そのサービスらしいか（例として、Duolingo は遊び心・よく褒める・失敗を責めない、Ameba は敬意を表す・快く迎え入れる、が挙げられている）
- VALUE: 使う人に良い変化が起きるか
- FUNCTION: ストレスなく使えるか

スライドはこの順に磨くとしている。この skill は仕様を変えない手直しなので、直す順番は重さ（誤操作 ＞ 迷う ＞ 見た目だけ）で決める。BRAND と VALUE は、同じくらい正しい直し方が複数ある時に選ぶ基準として使う。BRAND の言葉は、設定ファイルが指すブランドの文書から取る。文書に無い言葉を作らない。

## 機能 → 便益 → 価値 → 体験（スライド 24〜29 枚）

スライドの例（就活生向けのカレンダーアプリ）: 機能「予定を登録・確認できる」→ 便益「締切を見落としにくい」→ 価値「就活への不安が減る・楽しい」→ 体験「自分のペースで前に進める」。

画面の見立ての前に、画面ごとに 1 行ずつ書く。例（支払いの確認の画面）: 機能「金額と支払先を見て、支払いを確定できる」→ 便益「払う前に間違いに気づける」→ 価値「安心して払える」→ 体験「迷わず一度で払い終わる」。この 4 行に効いていない要素は、削る候補になる。
