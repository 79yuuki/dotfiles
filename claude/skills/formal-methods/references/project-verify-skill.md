# 検査をプロジェクトに残す・コードに追従させる

1 回きりの検査で終わらせず、次のエージェントが同じ性質を変更のたびに確かめられる形でプロジェクトに残す。残した検査は、コードが変わったら追従させる。

cursor/plugins pstack の `create-formal-verification-skill` と `maintain-formal-verification-skill` を、日本語に要約して改変したもの（MIT、`../../THIRD_PARTY_NOTICES.md`）。pstack の `/statechart` への参照は外した。

## A. プロジェクトに検査の skill を作る

### 対象を選ぶ

コードが利用者にしている約束のうち、破れると害が大きく、テストが届きにくいものを選ぶ。検査しやすいものではなく、リポジトリの中でいちばん強い候補を選ぶ。コードから答えが分かることは聞かない。ユーザーが場所や不具合を名指ししたら、そこから始める。

### 問いが道具を選ぶ

- 出来事が悪い順序で起きうるか → 設計の小さなモデルをモデル検査する（既定は TLA+）。
- コードが全ての入力で正しく動くか（メモリ安全、オーバーフロー、データ構造の不変条件）→ コードに直接かける検証器。その言語に無ければそう書き、手書きのモデルではなく、実コードを生成した入力で試す。
- 大きさに上限を置けない性質 → 証明。
- そのリポジトリの開発者が導入して実行できる道具を選び、選んだ理由を伝える。

### 良い検査の条件

- **コードに忠実。** モデルや証明の各部分が、レビューする人が開けるコードを指す。検査が 1 つの不可分な手順として扱うものは、コードでも不可分。名前はそのリポジトリのものを使う。
- **失敗できる。** 失敗するのを見たことがない検査は、何も証明していない。守っているコードを壊した変種（確認を外す、手順を入れ替える）で、性質ごとに失敗を見せる。
- **見つけたものは見つけたまま。** いまのコードが性質を破るなら、反例をコードの言葉で報告する。通るまで性質やモデルを弱めない。頼まれない限り製品コードを変えない。
- **範囲に正直。** 何を、どの境界と仮定で検査し、何を外したかを書く。通ったのはモデルか境界の中で、システム全体ではない。
- **道具なしで読める。** 性質と害を、それぞれ普通の 1 文で書く。反例は、コードの言葉で短い手順の列として語る。
- **安く再実行できる。** 1 コマンド、再現できる道具の版、次のエージェントが関係する変更のたびに回す気になる所要時間。
- **コードと歩調を合わせる。** 各検査が覆うファイルと関数、検査がコードを記述していると最後に確かめたコミット（sync commit）を記録する。

### skill を書く

`.claude/skills/<名前>/SKILL.md` に、領域と使う場面を書いた frontmatter を付けて置く。その skill だけを読んだ次のエージェントが、次の 4 つをできるようにする。

1. 変更が、検査されているコードに触れるかを見分ける。
2. 検査を実行する。
3. 本物の不具合と、モデルの誤りを見分ける。
4. 意図した変更の時に、検査を更新する。

覆う範囲の記録と sync commit を skill に入れる。sync commit を進めてよいのは、新しいコミットのコードを検査が記述していると確かめた後だけ、と書く。コマンド・path・名詞はそのリポジトリの実物を使い、穴埋めを残さない。

### 渡す前に証明する

生成した skill を、次のエージェントと同じように 1 回たどる。使い捨ての worktree（またはコピー）で、実コードに性質を破る捨ての変更を入れ、検査が捕まえることを確かめる。作業中のツリーは壊さない。捨ての変更を戻し、検査が元の状態（通る、または報告する予定の発見だけで落ちる）に戻ることを確かめる。一度も実行していない skill は下書きでしかない。捕まえ損ねたら、捨ての変更ではなく skill か検査を直す。

### 渡す時に伝えること

何を検査したか、どの道具をなぜ選んだか、境界、検査が見つけたことを普通の言葉で、実行の仕方、覆っていないもの。

## B. コードが変わった後に追従させる

コードが変わって検査が変わらないと、検査は「もう存在しないコード」を記述したまま通り続ける。この「通る」は証明に見えるので、いちばん危ない。

### 検査ごとに 1 つの結果を付ける

- **in sync**: 最後の sync から、検査が記述するものを変える変更は無く、検査は通る。
- **updated**: コードが変わり、検査が新しいコードを記述するよう直し、検査は通る。
- **bug**: 検査はいまのコードを記述していて、コードが性質を破る。これはコードについての発見で、ずれではない。
- **blocked**: 追従させられなかった、または実行できなかった。理由を正確に書く。

updated と bug は両立する。直した結果、検査がコードを記述するようになり、その上で性質が落ちることがある。

### 触ってよい範囲

検査だけを直す（モデル、ハーネス、性質のファイル、検査の skill）。頼まれない限り製品コードは変えない。性質が落ちても、通すために性質やモデルを弱めない。

### 手順

1. **検査を見つける。** モデル検査器・証明器・検証器を、名指しのコードに対して実行するプロジェクトの skill を探す。検査ごとに、性質、覆うコード、境界と仮定、実行コマンド、sync commit を集める。sync commit の記録が無ければ、検査のファイルを最後に変えたコミットを使い、そうしたと書く。
2. **そのまま 1 回実行する。** 何も変える前に結果を記録する。ここで通っても、コードが正しいとは言えない。古い記述がまだ成り立つ、というだけ。落ちても、ずれか不具合かは手順 5 まで決めない。
3. **覆うコードへの変更を全部読む。** sync commit から現在までの差分とコミットメッセージを読む。名前の変更・分割・移動も追う。検査が守る状態に触れる新しいコード（同じ項目に書く新しい関数など）も探す。変更ごとに、次のどれかを決める。
   - **影響なし**: 検査が記述するものを変えない（整形、コメント、覆っていない経路）。コミットメッセージではなく、モデルやハーネスと突き合わせて決める。
   - **検査がコードを記述しなくなった**: 1 つだった手順が 2 つになった、分岐が増えた・減った、確認の位置が動いた、守る状態へ届く新しい経路ができた、値の範囲が変わった。モデルやハーネスを直す。
   - **約束が意図して変わった**: 変更の中に、意図を示す証拠がある（doc コメント、テスト、変更履歴、コミットメッセージ）。性質を直し、その証拠を引用する。
   - **約束が破れたかもしれない**: コードは変わったが、約束が変わったという証拠が無い。この後の失敗は、不具合の候補として扱う。
4. **結果からではなく、コードから直す。** 再実行する前に、コードを読んで更新を書く。何が通るかに合わせて形を決めない。性質を変えるのは、約束が意図して変わった時だけ。古い文言、新しい文言、証拠を書き残す。境界は、変更で誤りになった時以外は保つ。縮めたら報告に書く。
5. **再実行して、結果ごとに判断する。**
   - **通った**: 直した記述が、失敗する力を失っているかもしれない。使い捨ての worktree（またはコピー）で、新しいコードを、性質が守っている壊し方で壊し（新しい確認を外す、新しい手順を入れ替える）、検査が捕まえることを確かめる。作業中のツリーは壊さない。
   - **落ちた**: 反例を、実コードの上で 1 手ずつたどる。コードで起こりえない手があれば、検査が誤っている。検査を直し、何が誤っていたかを書く。全部の手が起こりうるなら不具合。持ち込んだコミット、コードの言葉での手順、害を 1 文で書く。安いテストで再現できるなら、証拠として報告に添える。製品コードにはコミットしない。
6. **検査の skill を更新する。** 覆うコード、コマンド、境界、仮定、sync commit を直す。sync commit は、確かめたコミットにする。blocked の検査の sync commit は進めず、そう報告する。最後に、次のエージェントと同じように skill を 1 回たどる。

### 報告

検査ごとに、次を伝える。

- 結果と、読んだコミット。
- 検査の何を、なぜ変えたか（コードの形が変わった、または約束が意図して変わった。後者は証拠を添える）。
- 再実行の結果と、直した検査がまだ失敗できることを示すのに使った壊し方。
- 不具合ごとに、コードの言葉での反例の手順、害、持ち込んだコミット。
- まだ覆っていないもの。覆うべきなのに覆っていない新しいコードを含む。

どの失敗が検査のずれで、どれがコードの不具合だったかを、はっきり書く。直す前に通っていて、直した後に落ちた検査については、「前の『通った』は古い記述に対するものだった」と書く。検査の更新は、製品の修正とは別の変更にする。
