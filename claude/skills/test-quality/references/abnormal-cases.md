# 異常系の観点

異常は「どこから来るか」で 4 つに分ける。上ほどテストが書きやすく、下ほど見つけにくい。全部は試さない。「この処理が失敗したら何が起きるか」を考え、いちばん困る失敗から選ぶ。

## 1. 入力値の異常

- **境界値**: 最大、最大 +1、最小、最小 -1、ゼロ、負の値。例: 255 文字は成功、256 文字はエラー、0 文字は要件による。
- **今どきの境界**: ページサイズ（99、100、101）、ペイロードの上限、タイムアウトの閾値、レートリミットの境目。
- **同値分割**: 「1〜255」「256 以上」「0」のように組に分け、代表値と境界値を試す。
- **空の値**: `""`（許すかエラーか）、`" "`（トリムするかエラーか）、null（必須か任意か）、未指定（既定値は何か）。仕様が曖昧なら、テストを書く前に決めてもらう。
- **文字の種類**: 半角カナ、環境依存文字（㈱、①）、サロゲートペア（𠮷）、絵文字。DB の文字コードと API のエンコーディングに依存する。
- **攻撃になりうる入力**: HTML やスクリプトの断片、SQL の断片、シェルの区切り文字、`../` を含むパス。期待するのは「無害に扱われること」。
- **過去の不具合の傾向**: null の参照、ゼロ除算、日時の解釈、タイムゾーンをまたぐ日付（月末の 23 時台）。

## 2. 状態の異常

- **存在しない**: 無い ID を指定する。
- **削除済み**: 論理削除か物理削除かで、期待する応答が変わる。
- **処理中**: アップロード中、変換中、送金の確認待ち。
- **処理済み**: 同じ操作をもう一度送る。
- **権限が無い**: 他人のリソース、権限を外された直後。
- **不正な遷移**: 「作成 → 確定 → 発送 → 完了」に対して、「作成 → 完了」「完了 → 作成」を試す。

## お金の異常

お金を扱う処理では、上の 2 つに加えて次を確かめる。

- **金額の持ち方**: 仕様に合う表現（最小の単位の整数か、十進数の型）で持つ。二進の浮動小数点に変換される経路が無いこと。
- **丸め**: どこで、どの規則で丸めるかを仕様で決め、境界（0.5 の前後）をテストで固定する。
- **分ける計算**: 手数料や按分で分けた後、合計が元の金額と一致すること。端数の行き先が決まっていること。
- **台帳の不変条件**: 入った額と出た額の合計が合うこと。残高を履歴から計算し直した値と一致すること。
- **同じ依頼の再送**: 同じ識別子の再送は同じ結果を返すこと。同じ識別子で中身が違う依頼は拒否すること。
- **途中で落ちた後の再送**: 処理の途中で止まった後に再送しても、二重に実行されないこと。
- **応答だけが失われた場合**: 処理は成功したが応答が届かなかった時、再送で元の結果が返ること。

## 3. 環境の異常

- **ネットワーク**: 切れる、遅い、途中でオフラインになる。
- **DB**: 応答しない、接続が尽きる、デッドロック。
- **外部サービス**: 応答しない、レートリミット、想定と違う形の応答。
- **資源が尽きる**: ディスク、メモリ、ファイル記述子。テストで再現するより、監視で捕まえる方が現実的。止まり方（静かに止まるか、エラーを出すか）は設計で決める。
- タイムアウト、リトライ（間隔を伸ばし、ばらつきを入れる）、遮断の仕組みは、入れただけでは信頼できない。動くことをテストで確かめる。
- 手元の環境は、ネットワークも DB も安定していて、ディスクも尽きない。手元で通ることは、環境の異常について何も言わない。

## 4. 競合の異常

- **同時の更新**: A が読む → B が読む → A が書く → B が書く。どうなるべきかを先に決める（版の照合、ロック、後勝ち）。失うと困るデータに後勝ちは使わない。
- **二度押し**: 画面は送信中に無効化し、サーバーはリクエストの識別子で冪等にする。
- 競合は unit test では見つけにくい。順序の全列挙やモデル検査は formal-methods を使う。

## エラーの返し方

- 異常系のテストは、「エラーが起きないこと」ではなく「適切なエラーが返ること」を確かめる。
- HTTP の使い分け: 400 入力の誤り、401 認証の失敗、403 権限の不足、404 存在しない、409 競合、429 レートリミット、500 と 503 はサーバー側。
- 他人のリソースには、403 ではなく 404 を返す設計がある。存在することを推測させないため。どちらを返すかは仕様で決め、テストで固定する。

## テストの書き方

- テストどうしでデータを共有しない。ID を時刻から作ると、並列の実行で衝突する。UUID を使う。
- 作ったリソースは、テストの終わりに消す。
- 優先順位は、影響で決める。

| 優先 | 対象 | 頻度の目安 |
|---|---|---|
| 1 | セキュリティに関わる入力、お金とトランザクション、認証と認可の失敗 | 毎回 |
| 2 | 中核機能のエラーの経路、連携先の障害、境界値 | リリースごと |
| 3 | 込み入ったエラー処理、二次的な機能の端の場合 | 定期 |
| 4 | 安定した古い機能、利用の少ない機能 | 大きなリリースの前 |
