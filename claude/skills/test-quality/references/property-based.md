# Property-based test の書き方と落とし穴

ランダムな入力を大量に流し、「どんな入力でも成り立つ」性質を確かめるテスト。道具は fast-check（JS/TS）、Hypothesis（Python）、proptest（Rust）など。ここに無いオプションは、使う版の公式 docs で確かめる。

## 性質の選び方

- **対象が主張している性質だけを試す。** docstring、型、呼び出し元の使い方が約束していることを候補にする。約束していない性質で落ちても、不具合ではない。
- **入力の範囲は、呼び出し側から決める。** 呼び出し側が先に弾いている入力は、現実には来ない。
- 性質の型を順に当てはめて探す。

| 型 | 例 |
|---|---|
| 不変条件 | 残高は負にならない。借方の合計と貸方の合計は等しい |
| 往復 | encode して decode すると元に戻る。保存して読むと同じ |
| 逆の操作 | 足して引くと元に戻る |
| 別の実装との一致 | 速い実装と素朴な実装が同じ結果になる |
| 冪等・可換 | 2 回やっても 1 回と同じ。順番を入れ替えても同じ |
| 変換の前後の関係 | 入力を 2 倍にすると手数料も 2 倍になる。並べ替えても合計は同じ |
| 落ちない | 有効な入力なら、例外で落ちない |

## 落とし穴

- **入力を捨てて絞らない。** 「この条件の入力は捨てる」（Hypothesis の `assume`、fast-check の `fc.pre`）で絞ると、不具合の引き金になる入力まで捨てる。生成する側で範囲を決める。
- **既定の生成器の範囲を確かめる。** 既定の整数や文字列が、試したい境界（最大値、空、重複）を引くとは限らない。最小・最大・文字の種類を明示する。
- **弱い性質にしない。** 「null でない」「例外が出ない」だけの性質は、ほとんど何も確かめない。
- **正解を、試している実装から作らない。** 同じ壊れた処理を正解の計算に使うと、壊れていても通る。
- **落ちたら、3 つに分けてから報告する。** 性質の書き方が誤り／入力が現実には来ない／本物の不具合。
- **書いた性質が落ちることを 1 回見る。** 対象をわざと壊して（test-quality の手動の変異）、性質が落ちることを確かめる。

## 状態を持つ対象

残高・在庫・状態遷移のように、操作の列で状態が変わる対象には、操作をランダムに並べて流し、各操作の後に不変条件を確かめる（Hypothesis の `RuleBasedStateMachine`、fast-check の model-based testing）。前提が要る操作は、入力を捨てるのではなく、操作の前提条件として書く。縮小された操作の列を、具体的な回帰テストとして残す。並行と、全ての順序の探索は formal-methods を使う。

## CI での回し方

- PR の CI では、乱数の種を固定する。同じコードで結果が変わると、落ちた原因がコードか乱数かを区別できない。
- 新しい反例を探す実行は、種を固定せずに、別の定期実行で回す。
- 見つけた反例は、具体的な値のテストとして書き写す。道具が持つ反例の保存領域は、キャッシュであって正本ではない。
- 落ちた時は、再現に使う種や入力がログに出る設定にしておく。
