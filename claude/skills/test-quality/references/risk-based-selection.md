# 件数が多すぎる時の選び方（リスクベース）

AI にテストケースを書かせると、件数が増え続けて、リリースごとに全件を回せなくなる。減らすのは「今回回すもの」だけで、テストケースの定義は消さない。

## 3 つを分けて持つ

| もの | 中身 | 寿命 |
|---|---|---|
| テストの観点 | 機能ごとの「何を確かめるか」の一覧 | 残す |
| テストケースの定義 | 「この条件ではこう動く」を 1 行ずつ。仕様書を兼ねる | 残す。機能を変える PR で一緒に直す |
| 実行の記録 | 今回回すケースを定義から写し、結果を書く | リリースごとに使い捨て |

選ぶのは、実行の記録の上だけ。

## 影響度は「1 つの振る舞い」ごとに付ける

機能ごとに付けると、広い範囲のリファクタで全機能が対象になり、減らない。受け入れ基準（1 つの基準が 1 つの振る舞いを見る）ごとに付ける。問いは「この基準が満たされない時、使おうとした 1 人に何が起きるか」。

| 影響度 | 意味 |
|---|---|
| S1 | 目的を果たせず、代わりの経路も無い |
| S2 | 取り返しがつかない（直しても元に戻らない）、または収益に直結する |
| S3 | 目的は果たせるが、遠回りになるか体験が落ちる |
| S4 | 中核と関係のない付加機能が使えない |

## 起きやすさは、今回の変更から付ける

- 今回の変更で振る舞いが変わる基準: 高。
- 変わらない基準（コードの置き場所が移っただけ、波及しうるだけ）: 低。

根拠（どの PR のどの変更か）を添えて人に見せ、確かめてもらう。

## 選定表

| 影響度 | 振る舞いが変わる基準 | 変わらない基準 |
|---|---|---|
| S1 | 全件 | 全件 |
| S2 | 全件 | 正常系 1 件と、過去に不具合が出た条件 |
| S3 | 全件 | 過去に不具合が出た条件だけ。他は探索的テストで見る |
| S4 | 正常系 1 件 | 過去に不具合が出た条件だけ |

- 影響度と起きやすさを掛けて点数にしない。表なら、なぜ回すかを読んで説明できる。
- 回さなかった基準は、影響度と起きやすさを添えて実行の記録に残す。リリース後に不具合が出た時、判断を見直せる。
- 不具合ゼロと大幅な削減は両立しない。受け入れるリスクを、決める人と明示する。
- 単位を細かくしただけでは減らない。「どの基準を回さないか」を決めて初めて減る。
- 減らして空いた時間は、影響の大きい機能の探索的テストに回す（exploratory-qa）。
- 表は何度も作り直す前提で、人が読める文書を正本にする。skill やスクリプトと食い違ったら、文書が正しい。
