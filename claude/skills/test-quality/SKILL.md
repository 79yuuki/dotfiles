# Test Quality（テストの検出力を上げる）

テストの価値は「壊れを見つけられるか」で決まる。件数とカバレッジは、実行された行を数えているだけで、壊れた時に落ちるかどうかは教えてくれない。この skill は、既にあるテストを検品し、足りない所だけを足す。

変更と一緒に最初のテストを書く手順は test-driven-development にある。ここは、書き終わったテスト群を後から測る時に使う。

## 判定の物差し

1 本のテストについて、2 つの編集を想像する。

- **振る舞いを壊す**（誤った値、飛ばされた処理、二重の処理）。テストがまだ通るなら、そのテストは何も証明していない。
- **内部だけを変える**（外から観測できる結果は同じ）。テストが落ちるなら、そのテストは実装に固定されている。

1 つ目を捕まえ、2 つ目を生き延びるテストを残す。それ以外は書き直すか消す。

## 手順

1. **対象を絞る。** 全部は測らない。影響（お金・権限・取り消せない操作・状態遷移）と起きやすさ（最近よく変わる、過去に不具合が出た、同じファイルに修正が重なった）が高い所から、1 モジュールを選ぶ。
2. **ベースラインを取る。** 対象のテストだけを走らせ、green であることと所要時間を記録する。赤いテストがあるなら、先に直すか対象から外す。機械で数えられる臭い（assertion が 0 本、空のテスト、skip、sleep、テストの中の条件分岐）も、ここで数えておく。
3. **Mutation testing を 1 回かける。** コードをわざと書き換えた変種（ミュータント）を作り、テストが落ちるかを見る。ツールと最小コマンドは [references/mutation-tools.md](references/mutation-tools.md)。提出するブランチの依存は変えない。道具は、一時実行か、使い捨ての worktree の中に入れて試す。対象のファイルを指定して時間を区切る。ツールが動かなければ、隔離したコピーで手動の変異を 3〜5 個試す。
4. **生き残った変種を分類する。** 数が多い時は全部を読まない。1 行につき 1 つに絞り、影響の大きい所から読んで、残りは件数だけを報告する。ログ出力、計測、エラーの文言の変種は、対象の仕様に影響しないと確かめたうえで、まとめて「読まない」に入れる。有効・無効の切り替え、期限、上限の値の変種は、仕様に関わるので読む。

   | 分類 | 見分け方 | 対処 |
   |---|---|---|
   | テスト不足 | その分岐や境界を通るテストが無い | テストを足す（下の表から型を選ぶ） |
   | assertion が弱い | 通るテストはあるが、結果を見ていない | 期待値を仕様から書き直す |
   | 等価 | 書き換えても、外から観測できる振る舞いが同じ | 理由を 1 行書いて除外する。コメントや空白だけの違いは機械で除いてよい。それ以外を、モデルの判定だけで等価にしない |
   | 不要なコード | どの入力でも到達しない。消しても何も変わらない | 削除を提案する |

5. **足すテストの型を選ぶ。**（下の表）
6. **足したテストが効くことを確かめる。** テストごとに、狙った変種を入れると落ち、元に戻すと通ることを見る。落ちないテストは足さない。カバレッジが増えたことは、足す理由にしない。同じ対象・同じ設定でもう一度測り、生き残りがどう変わったかを見る。足したテストが、内部だけの変更で落ちないことも確かめる。
7. **報告する。**（下の形）

Mutation testing は、リポジトリ全体を CI で毎回回すものではなく、テストを直す時に使う道具として扱う。変更した行だけに絞れば、レビューのたびに回す運用も成り立つ。速い unit test に向いている。1 本が秒単位かかるテスト（E2E、DB を使う統合テスト）には、変種の数だけ時間が掛かるので向かない。常設（依存の追加、CI、日次の実行）は、1 回分の結果を見せてからユーザーと決める。

## 足すテストの型

| 状況 | 型 | 要点 |
|---|---|---|
| 境界・同値類・空値・文字種の抜け | 例示テスト | 観点は [references/abnormal-cases.md](references/abnormal-cases.md) |
| 「どんな入力でも成り立つ」と言える性質がある | property-based test | 往復（encode して decode すると元に戻る）、不変条件（残高は負にならない）、冪等（2 回やっても 1 回と同じ）、等価（速い実装と素朴な実装が同じ結果）。書き方と落とし穴は [references/property-based.md](references/property-based.md) |
| 1 つのプロセスの中で、操作の列によって状態が変わる（残高、在庫、状態遷移） | 状態を持つ property-based test | ランダムな操作の列を流し、各操作の後に不変条件を確かめる。縮小された操作の列を回帰テストにする |
| 既存の動きを壊さずに中身を置き換える | 特性テスト | 今の出力を記録して突き合わせる。時刻・乱数・順序を固定し、順番を逆にして 2 回記録して一致を確かめる。置き換えの安全網であって、不具合を見つけるテストではない。「今の動き」と「正しい動き」は別の物差しで測る |
| 正しさの基準になる別の実装や、移行前のシステムがある | 差分テスト | 同じ入力を両方に流して比べる。入力は乱数か本番の標本。空白など無関係な差を正規化し、意図した差は承認済みの一覧に書く |
| テストの対象がデータで列挙できる（設定、ルート、権限表、教材） | 生成テスト | データからテストケースを作る。足せば増え、消せば消える。生成したテストが壊れを見つけるかを、わざと壊したデータ（カナリア）で確かめる |
| 並行、分散、リトライ、全ての順序の探索 | formal-methods へ | 全列挙やモデル検査 |
| 画面をまたぐ業務の流れ | playwright-e2e へ | E2E は、どれか 1 つだけ選ぶなら最初に投資する型。ごまかしにくく、何が壊れたかを具体的に示す |

## 弱いテストの型

- mock が呼ばれたことだけを見ている。外部サービスが受け取る内容は振る舞いで、内部の helper の呼び出しは実装。
- 期待値を、試しているコード自身で計算している。または、いまのコードの出力から写している。AI が書いたテストで報告されている型で、不具合を正解として固定する。期待値は仕様・型・ドキュメント・issue から書き、出どころを添える。
- テストが自分で作ったデータに assert している。
- 異常系で「エラーが起きないこと」だけを見ている。見るのは「適切なエラーが返ること」。呼び出し側が分岐に使う型やコードを assert し、文言は assert しない。
- 「クリアになる」「200 が返る」だけで、結果の中身を見ていない。
- 時刻・乱数・実行順・他のテストが残したデータに依存している。
- skip・緩い matcher・snapshot の一括更新で green にした跡がある。snapshot は、大きいものと、時刻や ID のように揺れる値を含むものが弱い。

flaky なテストは、skip・sleep の追加・通るまでの再実行で隠さない。再実行は見つけるための手段で、green にする手段ではない。原因を、待ち方（非同期）／並行／実行の順番／時刻／ネットワーク／OS や環境／資源の解放漏れ、のどれかに分けて調べ、決定的にする。原因が見つからなければ、未解決として報告する。消す・隔離するのは人が決め、その時は担当、期限、代わりに何で確かめるかを書く。

## 毎回やらせている作業はプログラムにする

「○○を足したらテストも足す」と指示書に書いても、文脈が長くなると抜ける。同じ指摘を 2 回したら、生成テスト・lint・CI の check に変える。直す高さは、設計（間違った書き方ができない）＞ 型 ＞ lint・CI ＞ テスト ＞ 指示書の順。新しい check は、過去の実際の間違いで落ちることを確かめてから入れる。

## 件数が多すぎて回せない時

テストケースの定義は消さず、今回回すものだけを選ぶ。選び方は [references/risk-based-selection.md](references/risk-based-selection.md)。

## ガードレール

- テストを通すために、assertion を弱めない、skip にしない、期待値を実装に合わせて書き換えない。仕様が未確定なら、止めて聞く。
- 仕様から書いたテストが、いまのコードで落ちた時は、テストを直して通す前に報告する。落ちたのがテストの誤りか、コードの不具合かは、人が決める。
- スコアを上げるためだけのテスト（内部を変えると落ちるテスト）を足さない。良くないテストを足すより、足さない方を選ぶ。カバレッジを 100% に近づけること自体を目標にしない。
- 本番コードは変えない。テストしにくい設計（状態を書き換える関数、時刻や乱数の直読み、同じ判定が 2 か所にある）は、変更案として報告する。
- 数値には対象の範囲を添える。「mutation score 82%」ではなく「`payment/` の 3 ファイル、変種 120、検出 98」と書く。
- 測ったのは対象のモジュールだけ。他は未測定と書く。

## 報告の形

```markdown
## Test quality report
- 対象: （ファイル、テストのコマンド、コミット）
- ベースライン: （テストの数、所要時間、green）
- Mutation: （ツールと版、変種の数、検出／生き残り／タイムアウト／エラー）
- 生き残りの内訳: （テスト不足／assertion が弱い／等価／不要なコード。各件数と代表例）
- 足した・直したテスト: （何の壊れを捕まえるか。検出するようになった変種。期待値の出どころ）
- いまのコードで落ちたテスト: （直さずに報告するもの）
- 再測定: （同じ対象での変化）
- 提案: （設計の変更、常設にするか）
- 測っていないこと:
```

## Gotchas

- 境界の比較を変える変種（`>` を `>=`）の生き残りを「テスト不足」と数えたが、等しい時にどちらの式も同じ値を返すので、等価だった。分類の前に、元と変種で結果が変わる入力が 1 つでもあるかを、具体的な値で確かめる。
- 仕様の図と実装の表が 1 組だけ食い違っていた時、いまの実装の値をテストの期待値に固定してコメントで済ませた例があった。食い違いは報告されていたが、テストは通ってしまう。期待値を決められない組は、固定せずに比較から外し、`todo` として残す。
