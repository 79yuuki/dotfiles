## データ

- ソース: ローカルの `~/.claude/history.jsonl`（2025-10〜2026-10）。`/`・`!` で始まる行を除き、重複を除いた 1,364 件。

## 見つかった傾向

- 依頼の多くが、文末の形（「〜して下さい」「〜してほしい」「〜にして」「〜でしょうか？」「作れる？」「〜たい」）でしか依頼だと分からなかった。旧版はこれらを拾えていなかった。
- 旧版の語彙に無い作業語が多かった（刷新・改修・リデザイン・取り入れ・反映・検証・バックテスト・デザイン・UI・再発防止）。
- Codex へのレビュー/相談依頼や `/workflows` の指定が、新しい依頼にも続きの指示にも付いていた。旧版はこの定型句の「相談」「レビュー」「実装」に反応して、続きのやり取りでも発火していた。
- プランモードの承認（`Implement the following plan:`）、選択肢の回答、短い続きの指示、push・commit などの機械的な操作が、誤発火の主な原因だった。

## 変更

- 依頼/相談の文末（$req_ja）を追加し、作業語（$task_ja）と英語（$task_en）の語彙を広げた。
- 進め方の定型句を2段で取り除いてから判定するようにした。
  - Codex へのレビュー/相談依頼の節: 取り除くと作業の語（設計・移行・改善など）まで消える場合は、取り除かない（「Codexへの移行を相談したい」は依頼として残る）。
  - 承認待ちの節（「OKが出るまで改善して」）と編成の指定（/workflows・サブエージェント等）: 続きの指示なので取り除く。最後に、元の本文にあった新規作業の語（デザイン・設計など）が全て消えていたら、除去全体を取り消す。
  - 4,000 文字を超える本文は取り除かずに全文で判定する（続き・機械的操作の除外は 60 文字以下にしか効かないため）。
- 除外を追加した。
  - プラン承認
  - 60 文字以下の続き・選択（新規作業の語があれば除外しない）
  - 60 文字以下の「〜お願いします」（新規作業の語か、最適化・移行など FOCUS の語があれば除外しない）
  - 60 文字以下の機械的な操作（日本語・英語の作業語があれば除外しない。英語の操作語は単語境界つき）
- 「方針はそのままでいい」のように対象を保つ意味の「そのままで」は、opt-out として扱わないようにした（文頭・句読点・改行の直後だけ opt-out。間の空白は許す）。
- 文言を二段にした。
  - FOCUS: 設計・分析・資料・改善・自動化などの語がある依頼。triage 自体を省略してよいのは、同じタスクで triage 済みの時だけとした。
  - NORMAL: それ以外の依頼。明らかな Speed なら起動しなくてよい。

- ホールドアウトの 96.4% は、正規表現を見ずに書かれた文面での独立した値。取りこぼした2件を見て語彙を一般化した後は 100% になったが、失敗例を見て直した後の値なので独立評価ではない。
- 履歴で新版が発火した T のうち、FOCUS は 313 件、NORMAL は 81 件、STRONG は 3 件だった。
- S の発火は増えた（発火した 216 件のうち FOCUS 114 件・NORMAL 102 件）。
  - NORMAL では、明らかな Speed なら起動しなくてよいと伝えている。
  - FOCUS では、まだ skill を読み込んでいない・同じタスクで triage していない限り起動を省略できない。そのため S の約4分の1で、skill の起動1回分（読み込み済みなら triage だけ）のコストがかかる。skill の triage で Speed と判定すれば何も言わずに進むので、ユーザーへの質問は増えない。取りこぼしより拾いすぎを選んだ結果のコストとして受け入れた。
- C の発火（159 件）の内訳は FOCUS 77 件・NORMAL 82 件だった。
- 実セッション（`claude -p --model opus`、変更系ツールは禁止）:
  - 新規セッションの最初の依頼: 6/6 で Skill(ambition-lens) が起動した。hook を切っても 6/6 で起動したので、ここは description と superpowers の規則だけで足りている。
  - 途中で新しい依頼が来るケース: hook ありで 3/3、なしで 2/3 起動した。なしで外れたのはバグ調査の依頼で、systematic-debugging が先に起動していた。件数が少ないため参考値として扱う。
- 実行時間（3回測定）: 通常のプロンプトで約 30ms、200KB の文章で約 0.5 秒、引用符の多い JSON 200KB で約 0.4 秒、貼り付け 20 個を含む 1MB で約 0.4 秒、閉じ括弧 25 万個で約 0.5 秒だった。入力を倍にした時の伸びはほぼ倍。
  - jq 1.7 の match/gsub は一致1件ごとに本文を先頭からたどるので、一致が多いと長さの2乗で遅くなる（JSON 200KB の引用符への match だけで 15 秒）。join も要素数の2乗で遅い（20 万要素で 3 秒）。
  - 旧版から残っていた遅い処理を直した。末尾の空白を削る正規表現（空白 5 万文字で 33 秒）と、opt-out の判定前に引用を取り除く処理（JSON 50KB で 1.6〜2 秒）。引用の除去は split で分けて add でつなぐ処理に置き換えた（種類ごとの結果は正規表現と一致することを、ランダムな文字列 2,000 個で確かめた）。
  - 貼り付けの除去は正規表現のままにし、貼り付けが 20 個を超える 2 万文字超の本文は判定しない（無出力）。旧版はこの規模で 5 秒の timeout を超えていた。
  - テストに性能の回帰ケース6件を入れ、5 秒以上かかったら失敗にした。複数回の実測で、1件あたり今の実装では 0.02〜1.4 秒で終わる。concat を join("") に戻した変異と join を使う旧版では 4 件が 10〜22 秒、trim の末尾を "\\s+$" に戻した変異では空白のケースが 10〜11 秒かかり、どちらもテストが失敗することを確かめた。
- テスト: 合成ケース 117 件が macOS 標準の bash 3.2 で全て通る（bash 5 では未確認）。

## 残る課題

- C の誤発火の多くは、作業中のデザインへの指摘のように、新しい依頼と見分けにくいもの。文脈を持たない hook では区別できないので、skill の「同じタスクの続きは Skip」に任せる。
- ラベルは Sonnet による1回の分類なので、誤りを含む可能性がある。
- 1〜2週間、実セッションでの起動率と聞き返しの当たり外れを観察し、語彙を見直す。
